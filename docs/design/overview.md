# The overview

- **The overview as flow paths, in three forms to compare.** The overview draws the changed directories and the calls between them, and on a typical service that's controllers, services and repositories: the architecture, the same on every PR, so it says nothing about this one. It also made a box of every test directory whose tests it couldn't link to code, which in Java is most of them, since a test is in its class's package and another source root: on graal #15134 four of the strip's seven boxes were test directories. Boxes by module and layer were the first answer and were rejected for the first reason: a better drawing of what the reviewer already knows. What a PR has of its own is how it's reached and what runs from there, so the previews draw flow paths: each way the change is reached, a route, a page, a command, or the definitions nothing in the PR calls, with the changed files it runs in call order, new ones told from changed ones, and the requests it sends to the PR's own routes. Tests aren't on a path at all, nor docs, generated or mechanical files: they're listed under it by kind, every one a link to its code, so no changed file is missing from the page. Nobody knows yet which drawing reads best, so there are three behind a choice in the Display menu, Overview (preview), kept per browser, with Directories, the first overview, the default until the data flow took its place (below). **Lanes**: a column per directory, callers first, and a row per path with no lines between its marks, so the architecture is the table's headings, read once, and a mark is only where this PR changes something. **Bow tie**: where the change is reached on the left, the directories it runs through in the middle, what it ends in on the right. **Flow rows**: no diagram, a small tree of chips per path, each file after or under one that calls it. A path runs definitions, not files: a call into one method of an added class reaches that method and what it calls. By file was the first version, and on graal #15134 a one-line call was a path of 17 files, 15 of which it doesn't run. A link between two files is a call the path makes, in every form: the first version drew each path as a chain of its files, and a third of graal's arrows joined two files with no call between them. On delphi-code #2 that's four paths, the page's ending in its three requests to the routes; on graal #15134 ten, over eleven directories, which lanes scroll sideways for. They're as good as the entries that are recognized: megareviewer #3 has five paths from the components of three files, and the rest start at definitions nothing in the PR calls, an override or a callback a framework reaches. Code outside the PR that uses what it changes is a count on the changed file or directory, “used in 4 places outside the PR”, and starts no path and has no box in the overview's directories. A row or a faded box for each such file was the version before: a regression would show there, but on graal #15134 they were 13 of 19 rows, 11 of 20 boxes and 17 of 31 edges, and the reviewer reading what the PR does was looking at files it doesn't touch. Where the code is used is read where it is, on its card in the map. What a path ends in beyond a request, a table written or a service called, isn't known without the model, and an unchanged route that reaches changed code through several calls needs callers of callers from the checkout. One form, picked by us, was the alternative; three cost little while they share one model, and two of them go once reviewers have used them.
- **The overview is how data moves through the change, written by the model.** The directories and the three previews all draw the call graph of the changed files, and none of them read: on graal #15134 that's 16 boxes or 49 chips, with lines that say who calls whom and nothing of what passes. A call can push data, pull it or do neither; the code that keeps data is where its writers and its readers meet without calling each other, and in a call graph it's only something everyone calls; and a type that's passed around is drawn as a place. What's under each diagram, Not linked, On no path, Also changed, is named for what the layout couldn't place, there because every changed file had to be on the page, which the file tree already is. So the Overview is one column, read top to bottom: where the data comes in, a few **stations** it passes through in the order it moves, and where it ends up. A station is a role and not a file: its name in words, the files that play it, files that end alike as one chip ("4 × …InstrumentationPhase"), when it runs where the stations differ in it, and whether it keeps data for a later station, said by a double border and in words. Between two stations is what the first hands the second, as data, with the files that only define it. Existing code the change edits is dashed, on the station it reaches, with what it calls there by name: those few-line edits are where the change meets the rest of the system. Under the flow one line counts what it leaves out, by kind, each opening to its files, so the flow's lines and that line's are the pull request's.

  The model writes it, in the steps pass, with the tour: the source, the stations with their files, and the end. Doing it in code was tried first, on graal #15134's analysis: files grouped by the words their names end with, each edge turned to point the way data moves by whether a call passes arguments and uses its result, and labelled with the methods called. It left 29 stations and 57 arrows. Which five things are the stations, which type is cargo and which class is a store is a judgment, and rules on names don't make it, as they didn't for risk. The server checks what the model wrote: a file has to be one of the pull request's and is in one place, a station without one is dropped, and two neighbors that no call, use, request or import joins are told to the one retry, and after it kept with their arrow dashed and "Not checked" in words, since dropping a station would hide a stretch of the path. A pass of its own was the alternative: one more call that reads the pull request, and a second telling of the change beside the tour's. The steps as the stations was the other; a step is one thing the change makes true with the lines that show it, in the order of what matters, and a station is every file of a role, in the order the data moves. One path only: branches are how the diagrams stopped reading, and the rest of the change is in the line under it.

  Without an AI review the Overview is its directories, as before, under one line saying why. That's the page being as good without the model as it was, not better: nothing deterministic that read well was found. A run asks for the steps pass while the Tour switch is on, or the Overview is on and its form is Data flow, the default, so the flow doesn't depend on a switch named for the tour. Directories and the three previews stay in the Display menu's choice until reviewers have used this one. Not known yet: what the model writes on a real pull request. The prompt has run on none, and the evals score no flow.
- **The overview is off until the reviewer turns it on.** None of its forms has earned a place on every review yet: the data flow hasn't been written for a real pull request, and the directories and the three previews are still being compared. So Overview is a switch in the Display menu, off by default and kept per browser, and while it's off there's no Overview in the bar's switch, `?view=overview` stays on the code, the menu has no Overview (preview) choice, and a run asks for no data flow; with no tour either, the bar has no switch at all. The Overview always in the bar's switch was the version before, a button on every review for a layout still in preview.
