# Findings

- **A point is a finding.** What the model asks the reviewer to look at is what looks wrong: a finding, or an intent mismatch no finding names, in one ranked list. A finding is a draft comment under the line it rests on, with its type, Claude's severity and a suggested change when the fix is a few lines; the type and the severity are Claude's and stay on its card, so the comment the reviewer adds, and every comment on the PR, carries neither. Add to review saves it as the reviewer's draft, Edit opens it in the comment box first, and it posts with the review under their name; Dismiss folds it. Once posted, it stays folded above its thread: a finding beside the comment made from it says the same thing twice. Its lines are marked on their numbers, in its severity's color. Silence means fine. Nothing else is a point, and nothing else becomes one: a finding says something looks wrong and asks for a change, and a choice that's intended but has a consequence isn't that. What nobody asked for is an intent mismatch, and so is what changes for existing code, users or data without being asked.

  Two other kinds were the version before, and neither earned its place. A **risk** was a hunk the model marked contract, with its reason, as a note under its lines: code worth reading closely, with nothing wrong. It was a classifier's output shown as a point, and a classifier can't triage: every hunk it marked was a card that asked the reviewer to stop, 25 of them on delphi-code #2 and still 8 after the prompt kept only where a mistake would break something outside the PR, and reviewers read them as noise. A **decision** was why the code makes a choice, a chip at the end of its line that opened a footnote. It was off until a switch in the Display menu turned it on, because with it on a PR whose description explains its choices read them twice, six of eight times on delphi-code #2, so nobody opened it. Before that the two were cards of a finding's shape, a band over the code, a margin bar, and approve and reject on each decision, seven clicks to say "fine". A risk also named the test that checked it, when one did: "Checked by `answers 404 for another user's order`". It answered "should I stop here?", and there's no risk left to ask it of. A preference such as "any change to billing" used to make a hunk a risk, and then the brief's Watch line said first that the change touches it; now a finding carries its mark when something there looks wrong, and nothing is said when nothing does.
- **A finding is about logic, a contract or the architecture.** The findings pass looked for bugs only, and two things a reviewer is there for went unlooked for: what the change breaks outside the PR, and whether it's built in the right place. It now looks for three types and says which each finding is. **Logic:** the code does the wrong thing. **Contract:** the change breaks or exposes something outside the PR, a caller, stored data, a security boundary, a user or another service, a dependency or configuration. **Architecture:** it's built in the wrong place or the wrong way for the code the PR shows. A finding that's both is contract, since outside the PR wins. Contract is the name a hunk's risk class has too, on purpose: both mean the boundary between the PR and what's outside it.

  The bar is the one a logic finding always had, what's wrong, shown by code the model read, and a change to ask for; without it the risks would be back as minor contract findings. So a contract finding names who breaks and shows it: "`chargeOrder` in billing/charge.ts still multiplies by 100", not "this changes the response shape". A change that only could break something is no finding. For that the model reads the unchanged callers, which is where a contract break shows and which only the page showed until then; a run started before they arrive reads the PR without them. An architecture finding rests on what the PR and its callers show, since the model doesn't read the codebase, and "this belongs elsewhere" is a guess unless the elsewhere is in the data. It's one of three things: a dependency that points the wrong way between files in the data, a layer the other code goes through and this code skips, and logic written again that code in the data already has. Naming, style and "consider" stay out for every type. Architecture was to be dropped if it brought wrong findings; on the evals it brought none, in two cases made for it, so it stays with that said.

  A type is a label and a filter: a word on the card, and a filter in the list of findings, which narrows the rows and what Previous and Next walk to that type, without moving the page. Sections by type were the alternative; a run has at most 10 findings and usually a few, so a heading would often sit over one. A chip per type on the bar was the version before: the chips looked like badges, read louder than the stepper beside them, which was three borderless words, and left the findings looking like counts to read rather than something to go through; a filter on the bar is room spent for a run of at most 10. **Severity ranks.** The bar's pager and its list go blocking first, then major, then minor, in the model's order within each; the model's order alone was the version before. **Severity takes the colors:** a finding's marks, its bar and its glyph are blocking red, major orange or minor amber, each with its word on the card. A color by kind, a finding red, a risk amber and a decision grey, was the version before, and a color per type was rejected: three more hues that mean nothing until learned, on a page where red, orange and amber already read as levels. A mismatch no finding names has no type and no severity, comes after the findings, under no type's chip, and is grey.

- **Contract is the rules' alone.** A hunk's risk class, *mechanical*, *logic* or *contract*, comes from a mechanical proof or a rule on its file's path, and is internal: it orders the flows and is never shown, since a rule reads the path, not the code. The model no longer classifies hunks, so a run changes no hunk's class. A count of contract parts in each file's header, the tree and the overview was one version before, with the rule's reason ("auth or security path"): it said where to look without saying why.
