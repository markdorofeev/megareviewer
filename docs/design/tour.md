# The tour

- **A tour of the PR, to understand it before reading it.** Between the brief's three lines and the files, nothing said what the change does and how, so understanding a PR meant reading it. The tour is a few steps, what matters most first, each one sentence of something the change makes true for someone outside the changed code, a user, a caller, an operator, or code that was there before and now behaves differently, and the lines that show it, real diff lines the reviewer comments on as in the map. The first step is what the change is for, on the most outward lines it has: the page, the route, the option. Call order was the version before, from where the change is reached to what it ends in, each step what happens at one hop: the third principle's story, which the overview's flow paths still tell. It said how a request runs and left out what a reviewer most needs said. On delphi-code #2 it opened on a page's query setup and never said that a saved token is now used for cloning too; on graal #15134 it followed the instrumentation from the feature to the profile file and never reached the inliner's size count, changed in shared compiler code, nor the listener that now runs on every thread before any Java code. Asked for what the change makes true, the same model said all of these and opened graal's tour on the option's own help text, in one run of each task on Sonnet 5.5. A step is then no hop of a path, so it shows one place or two, in one file too; two only across a process, each in its own file, was the rule before. The heart of the change first was tried on the same two pull requests: on graal #15134 the model took the entry point for the heart and followed the calls from there, and on delphi-code #2 it gave the same steps as when asked for what the change makes true. Steps as the author's decisions or as a reviewer's questions were the other ideas, and weren't tried: decisions were points once and said the description again, and which questions to ask would be the model's choice. In about two minutes the reviewer knows what the PR does and how, and whether anything is fundamentally wrong, then approves from the bar or goes to the code. It's a layout of its own, Tour, the third in the bar's switch beside Code and Overview, there once a run has written a tour: a strip of the directories the steps' lines are in, the steps, then what the tour didn't show, every changed line no step shows, counted from the diff by file, so the steps' lines and the ledger's add up to the PR's; and Claude's findings outside the steps. The model writes only the steps, in a pass of its own; the boxes are the overview's directories and the chips on a step are the analysis's points on its lines, so nothing in the tour is a second wording of what the page already says. A suggested depth after the findings, which steps to read in the code by a rule, those with an open finding, was the version before, under a heading of its own, After the tour: it mostly said that no step had one, and a step's chips already say which have findings. The tour is on unless the reviewer turns off the Display menu's Tour (preview) switch, and the page still opens on the code. Off, the page is what it was before the tour, and so is every request once the Overview isn't its data flow, which the same pass writes. Off by default was the version before: a reviewer who hadn't found the switch never saw a tour, and one who had turned it on every time megareviewer started, since the choice is kept in the browser's storage and without a fixed `--port` every start is a new origin. Now it's turning it off that has to be repeated, which costs the reviewer who does one more pass that reads the PR from the cache: on delphi-code #2 $0.05 of a run's $0.74, done before the findings were. Without a tour there's no Tour in the switch, and the Overview is its diagram with a tour or without. The Overview showing the tour in place of its diagram was the version before, with a line saying why when there was none: a reviewer who wanted the directories after an AI review had lost them to the tour, and the switch's second button meant two things. Open in code shows the map on a step's lines, marked on their numbers in the primary color under a label naming the step, and the bar's switch, Esc and the browser's Back come back to it; the bar's switch goes between the step last current and its lines. A second row under the bar, Back to tour, was the version before: the switch beside it already went back, so it said the same thing twice in a row of its own, and Understand was the layout's name while it showed the tour, so the switch's second button changed its name with a switch in the Display menu. A spotlight over the map, dimming the code a step doesn't show, would have kept the file order the tour exists to get past; the tour as the first screen would have put a model's reading in front of every review, the intro panel reviewers skipped. The designer's version differed where the product does: its ledger listed files without a step, so a step showing 8 of a file's 164 changed lines left 156 in no list; without the model it drew a flat row of boxes, worse than the overview; while the passes ran it counted directories read, which nothing knows, since the passes read the whole PR at once; it added a row under the bar with a second Display menu, a line of code on every screen; and its Esc left the tour for the code while the map's Esc came back, so the two bounced. A step's chips open the point's card in the map rather than dismissing or raising it in place, and steps have no keys of their own.
