# Analysis pipeline

Input is a PR URL from either host. Output is one analysis, cached by `(host, repo, PR, head SHA, pipeline version)`, so reopening a PR is instant and a new push triggers a fresh analysis. Neither the model nor the checkout is in the pipeline version: both add to the analysis.

**Callers are added in place.** An analysis is complete without a checkout, and its callers come when one is found. `startFor` looks for a checkout when a PR is first analyzed and whenever a complete analysis without callers is opened. With one, it's read: by the code's stages, or, on a complete analysis, before the open answers, so a reviewer who runs `git fetch` in their clone and opens the PR again has the callers on the review they left. With none, the analysis says `downloading` in the write that completes it, the commit is downloaded, and the callers are added under the same ID, so the reviewer's drafts, verdict and place stay. The code's stages run again in memory with the checkout (`checkoutFields`), and only `unchangedCallers`, `checkout`, `checkoutDir`, `checkoutError` and the checkout's warnings are written; the callers' parts are the analysis's own, since prep is deterministic and a checkout changes nothing else in it. The warnings also go into `beforeModel`, so Remove AI review keeps them. The download starts once the code's stages have ended, so it doesn't take the line from the review's own requests. On delphi-code #2 the review is complete 3.5 s after the open's answer and the callers come 0.8 s later; on graal #15134, 6.6 s and then 17.2, of which 13.0 is the download.

A model run keeps the analysis it started from and saves it whole, so a change written under one would be lost. Callers are written only while none is in flight, and a download that ends during a run waits for it; the write is a moment, and a run about to start waits for it and then reads the analysis it starts from. A run started during a download doesn't wait, and reads the PR without the callers. While it downloads, the analysis is still followed (`following`), as while a guardrail call runs, so a run's end is announced as an update and `done` comes with the callers. A stop during a download leaves `downloading`, which the next start sets back to what the lookup had found.

The key said whether a checkout was read until then (`20+checkout`), since the callers were decided before the analysis started: a checkout that gained the commit meant a new analysis under another ID, and the reviewer's drafts stayed on the old one. Version 21, which dropped the risk and decisions passes, dropped the lookup under that key with the cache it served. Version 22 gave findings a type. Version 23 is that line of work and the flow paths' together: on the branch they were merged from, 21 recorded the definition calls and dropped comment lines from changed definitions, and 22 reached a member only through the class its receiver names, so an analysis stored as 21 or 22 by either has what the other changed wrong. Starting the download with the analysis and waiting for it in prep was the alternative: the review would open after 13 s instead of 6.6.

An analysis is complete after prep, with the model's stages not run (`skipped`). The model passes run when the reviewer asks for them on the page, with Request AI review (`POST /api/analyses/:id/model`, with the chosen option's ID or none for the default, and `tour` when the page's Tour switch is on; an unknown option is a bad request, and one that can't run is refused with its reason), on that analysis in place, so the reviewer's drafts, verdicts and place stay. The run collects and preps again from the stored PR, its files from `file_contents` and prep being deterministic, then runs the passes. Its failure is the analysis's `modelError`, shown beside the button with Try again; the analysis stays complete, so the reviewer keeps reviewing while the passes run. An analysis is in progress while its code's stages or the model's run, and its events stream until neither does. Starting the same PR's analysis with the model on, under another ID, was the alternative: drafts are kept per analysis and wouldn't follow. A model run a stop interrupts is failed at the next start, as an analysis is.

Remove AI review, beside the usage line under the code, takes a run off again (`DELETE /api/analyses/:id/model`) after asking, so the passes can be tried again on the same PR: what the code made is put back in place under the same ID, and the states of Claude's points go with it, so a new run's `f1` doesn't take an old one's dismissal. The reviewer's drafts and a publication's record stay. A run changes one of the code's fields, the warnings, which it adds to, so the first run on an analysis keeps them as the code made them (`beforeModel`), and removing the run puts them back and clears the model's own fields in one write, reading nothing from the host, Jira or the checkout and parsing nothing. A run stored while the model classified hunks kept the risk too, which it changed, and that's put back the same way. The answer is the analysis as it now is, and the page starts afresh from it, keeping the reviewer's place, without loading it again. Running the code's stages again in the background was the first version: on delphi-code #2 they took 0.45 s, 0.9 s on a server that hadn't parsed yet, and then the page fell back to a skeleton, which sent the reviewer to the top, and loaded the analysis again, which asks the host whether the PR has moved once a minute: 0.74 to 0.85 s from the click to the page, 2.9 s when it asked. Now the request takes 12 to 40 ms and the page is back 0.44 to 0.56 s after the click, in headless Chrome on a machine under load. An analysis whose run started before the fields were kept runs the code's stages again within the request, in 0.4 to 0.5 s, and is left as it was if they fail. Keeping the model's warnings apart from the code's was rejected: every reader of the warnings would have to merge them. Every model call is kept with the analysis, a failed one too: its pass, attempt, start, duration, and what came of it, an answer, the problems the checks found in it, which a retry is told or the server mended, or the error, with why. Run details, beside the usage line, lists them in the order they started, timed from the run's first call, and the server logs each with the same fields. Both name the run's option, "Sonnet 5.5 through Claude Code", which the analysis records when the run starts; analyses stored before the choice have none, and were all Haiku 5.5. On delphi-code #2 the findings pass ran twice and took 4 of the run's 5 minutes, and nothing said why: usage kept only the calls that answered, without their problems, and the log line said how many problems there were, not what they were, in a terminal that was gone by the time anyone asked. Keeping it in the log alone was the alternative; a run is looked at on its page, often long after the server that ran it.

## 1. Collect

- PR title, description, branch name, commits, and the diff, from the host connector.
- Base and head contents of each changed file, for parsing and context.
- Jira tickets: keys matching `[A-Z][A-Z0-9]+-\d+` in the description, commit messages and branch name, fetched from Jira.
- Whether a checkout has the PR's head commit, looked for before the analysis starts.

## 2. Deterministic prep (no model)

- Split the diff into hunks with stable IDs. Every later stage refers to hunks by ID.
- Mark hunks as **mechanical with proof** when a check proves it:
  - generated or vendored files (lockfiles, `linguist-generated` in `.gitattributes`, known build output);
  - whitespace-only changes;
  - pure renames (rename headers in the diff with no content change);
  - moved code (removed and added blocks match after normalization);
  - formatting-only changes (tree-sitter syntax trees are identical before and after).
- Split each hunk without a proof into **parts**, one per definition it changes. A hunk is whatever git put between two unchanged stretches, so one can hold three routes, and the flows could place it only once: on delphi-code #2, three routes added in one hunk made one flow of 32 of the 48 hunks. The cut is at the outermost definitions that start or end inside the hunk, so a class around a block of methods cuts at its methods. Deleted lines go with the definition around them in the base file, and an unchanged line shared by a base and a head definition makes them one, so a renamed method stays one part. Lines outside any changed definition (imports, decorators, comments, unchanged stretches) join the next part. Tests split too. A proved hunk is never split, since its proof is about the whole hunk. Proofs, decisions, comments and risk stay per hunk; hints and the flows are per part.
- Build call-graph hints with tree-sitter: which changed symbols are defined, and which changed code calls or uses them. A use links to a definition only in its own file or in a file its imports reach, never across languages or from code into tests, and a type annotation isn't a use. A member reaches a definition through what it's written after, its receiver, as the parser reads it in Java, Python, TypeScript, JavaScript and Go: a receiver that names a class or type of the PR or of the caller's file reaches only that class's members; one the file imports reaches only what that import reaches; in Java, a type's name that's neither, `NodeClass` or `Math`, is a class outside the PR and reaches nothing. A receiver that names no class or import, a variable, a field, `self`, `this`, a call or a longer path, reaches as before, since nothing says which class it holds. Matching the member by its name alone was the version before: on graal #15134 `TYPE = NodeClass.create(BranchProfileCounterNode.class)` reached `BranchProfileRecorder.create`, and `TypeProfileRecorder.isEnabled()` every recorder's `isEnabled`, 199 of the 1,028 hints and call sites, and with them 144 of the definition calls the flow paths follow. Following a variable to its declared type was the alternative for the rest: it needs the type of every local, field and parameter, a resolver of each language, and an inherited member would still be missed. The same rule holds for the unchanged callers. The pipeline version went up with it, since analyses stored before hold the wrong links. Matching names across the whole PR was the first version: on a real PR it linked Python and TypeScript files that shared a class name, pointed production code at test fakes, and joined most of the PR into one tour step. A missing link hides no code, so the hints err toward fewer.
- Find the **call sites**: every use, on a part's lines, of a definition the PR changes, by the hints' rules, with its line and column, for the page to show the code a call runs. A hint keeps the first line a name is used on, at most 10 per hunk, and the first part that changes a definition, which is what the tour needs; a site is every use, uncapped, reaching every part that changes the definition. On delphi-code #2 that's 128 sites beside 105 hints. The parser gives each reference the column of every use on its line, in UTF-16 units, as the page's strings count.
- Find the **definition calls**: what each changed definition runs among the others, by the hints' rules, uncapped and within a part too, for the overview's flow paths to follow. A call goes from the innermost definition around it, or from the part's lines outside any. A function runs the ones written inside it, and naming a class reaches its own lines and its constructor, never its other methods. An added file is one part, its class, so a hint into it reaches everything the class does: on graal #15134 a one-line change in `CodeInfoEncoder.java`, a call to one static method of `StackSampleRecorder`, "ran" 17 files, and the two lines of `CompileQueue.java` 28. By definition each runs 2. A field's initializer runs only where the field is named: followed with its class, as Java runs it, every recorder a path named led through its constants to the profile writer. Cutting added files' parts at their members was the alternative: the hints would be finer too, but a part is also what the map shows, points sit on and the flows place, so an added class that two flows read would be in pieces, or joined back and its hints with it. Naming the definition on each call site was the other; a site leaves out calls within its own part, and those are how one method of a class reaches the next. On graal #15134 it's 1,432 calls among 780 definitions, 71 KB of the analysis's 1.7 MB. An analysis stored before has none, and the pipeline version went up with it, as it does when prep changes what an analysis holds: otherwise an open PR would keep its old paths until its next push.
- Link changed files by their imports, by the same rules, for the overview: an import that reaches another changed file is a link, even where no hint does, such as an app importing the module that registers its routes.
- Link requests to routes, across languages: a call that names an HTTP method and a literal path (a typed or generated client, `fetch` and the like, a test client in a test) links to the part that adds the route serving it. Methods match exactly and paths segment by segment, a placeholder in any syntax matching one segment. A base prefix the client adds isn't in the code, so a request also matches after dropping its leading segments, but only when that leaves one route. Hints stop at a language, so a full-stack PR was two islands: on delphi-code #2, nothing linked the page to the three routes it calls.

- With a checkout, find the **unchanged callers** of what the PR changes: code outside the PR that calls a definition the PR changes, or names it as a type, which is where a regression shows. A changed definition is one the base file has and whose own lines the PR adds or deletes, not counting nested definitions, blank lines or lines that hold only a comment, which the parser finds by the language's syntax, on either side of the diff, so a class that only gains methods isn't one. Counting comments was the version before: the Javadoc above a method is in its class, not in the method, and on graal #15134 three types that only gain members with their Javadoc, `CallTree` the first, brought 150 of the 191 uses the brief's Watch line counted then. Now 26 are found. Callers are found by the hints' rules: through imports (or the package, in Go and Java), within a language family, never from code into tests, and not type uses of generated files. Only files in the PR's languages whose text names a changed definition are parsed, and languages whose imports aren't read are left out. At most 50 uses per definition are kept, code first, with the rest counted. Matching names across the repository was measured first: on delphi-code #2 it found 357 uses in 83 files, almost all other things named `state`, `to_json` or `main`. Following imports leaves 6: `create_app`'s three callers, the one of `clone_credentials`, whose order of credentials the PR changes, and the page that renders `CredentialsGuide`. One level only; callers of callers would need the same reading again.
- Classify every remaining hunk as *contract* or *logic* with rules on its file's path: dependency manifests, schemas and migrations (an `openapi*` or `swagger*` file among them), CI and infrastructure, repository config, app config, and auth or security paths. A rule can only raise a hunk to *contract*; one no rule matches is *logic*. The rules read what a file is, never the names or text in it. A security path skips test code (tests, and helpers named fake, mock, stub or fixture), and doesn't make a hunk contract when every line it changes is inert: blank, a comment, an import, a string, an UPPER_CASE constant set to a literal, a closing bracket, or, in markup, a tag with literal attributes or plain text. The rules' contract is internal: it orders the flows, and the page never shows it. The model doesn't classify hunks, so a run changes no hunk's class; a risk pass that marked each one was the version before, and what it marked contract was a card on the page (see [docs/design/findings.md](../design/findings.md)). Line rules were the version before that: credential storage and authorization read from the shape of a name (`save_secret`, `require_permission`), credential endpoints from a changing route with a `token`-like segment, risky calls from regexes on added lines (`eval(`, `subprocess`, `shell=True`), and removed or skipped tests from counts of declarations and skip markers. Probed with counterexamples, each failed both ways: a lexer's `clear_tokens()`, `Notification.requestPermission()`, `POST /llm/tokens`, "subprocess" in a log message and two tests merged into one were contract, while `localStorage.setItem("token", …)`, a removed owner check, a removed `@login_required`, `POST /login`, `spawn("sh", ["-c", cmd])`, `pickle.loads`, a deleted assertion and `@unittest.skip` were logic. Risk is about behavior, what a check guards, what a response exposes, what an assertion still proves, and a name doesn't say it; longer word lists only move the edges. What a name can't say is the findings pass's, with Request AI review. On delphi-code #2 the line rules made 10 hunks contract and path rules alone make 3: keychain.py, on a security path, and openapi.json's two.
- Build the **flows** from the call-graph hints. The page doesn't show them as steps (see [Map](ui-layouts.md)); they order and label the overview, and the page's tour is the steps pass's (see [Model passes](model-passes.md)). A flow starts at an entry point a user or caller reaches (an HTTP route, a page, a command), found by framework markers on added lines, and reads the changed code it runs, callers before callees. Code that more than one flow runs is read once, in a shared section before them, and the flows that run it come after it: one section per connected piece of shared code, with the tests of that code, titled `Shared:` and where the flows enter it. A section is a flow without entries. Reading shared code in the first flow that reached it was the first version: on delphi-code #2 the GET flow read 37 of 73 parts, most of them the connection and keychain code that PUT and DELETE run too. With shared sections the largest step has 23 parts and GET 21, and every part is still placed once. Code an earlier flow read isn't read again. Types, imports, tests and docs join the flow they belong with; what no flow runs goes into supporting steps: API schema, docs, tests, and other changes by area. Shared sections come first, then flows that reach contract hunks. There's no cap on how many flows there are: merging unrelated code to meet one would hide the story. Grouping the files the call graph connects was the first version: its steps were whatever happened to connect, titled by a chain of symbols, and on a real PR one step held 33 of 48 hunks. Code that registers an entry, like a router the routes are declared on or an app adding that router, is read first in the first flow it registers. A request never extends a flow: a flow that sends one comes after the route's flow. A page flow that walked into the backend would read the whole PR. A test that requests a route joins that route's flow.
- Join back the parts the flows read together: consecutive parts of one hunk in the same step become one part again, and a hunk read in one step is whole again. Splitting without joining gave 115 parts on delphi-code #2, one file in 29 pieces, too fine to read; with joining, 8 of its 48 hunks stay split, into 32 parts, and each of its three routes is a flow of its own. The model's passes see whole hunks: its input maps hints back to hunks.

Proofs, risk classes and flows are the code's alone: no model run changes them.
