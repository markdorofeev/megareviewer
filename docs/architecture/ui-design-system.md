# Design system

The UI is Indigo Calm: Tailwind CSS v4 utilities over its tokens, in `web/src/styles/globals.css`, kept as the design handed it over except for the dark surfaces, with its fonts served from the package: Geist and Geist Mono for the chrome, JetBrains Mono for code and Inter for the file tree. It has a light and a dark theme, the dark one on a neutral grey ladder from `#1F1F1F`, with the diff, verdict and risk tints lifted to match. Cards, gutters and threads are `#1F1F1F` too, flush with the page and set apart by their borders; a step lighter, `#262626`, was tried first. The design's near-black, blue-tinted ladder from `#0B0B0F` was the first version. Where the lighter surfaces failed the contrast check, the foreground was lightened, never the surface darkened, so comments in dark code are now only a little dimmer than the text. and a diff palette safe for color blindness, blue and orange for green and red, chosen apart from the theme; both are kept per browser, and `web/public/theme.js` sets them before the first paint. That's a file rather than an inline script because the server's CSP allows scripts from `'self'` only. The two risk classes the page shows, logic and mechanical, are greys. Contract had a hue while the model's contract was a point: amber, so a finding, a risk and a decision read as red, amber and grey, magenta before that, the one hue no diff, verdict or focus color used, which read as another category rather than a level, and a teal logic bar on nearly every part in the first version, which said little. The AI review's controls are the primary as a tint, `ai-soft`, 8% of it over the background in both themes, with borders at 38% and, for new commits, 65%; the design's 14% in dark put the label on its hover under 4.5:1, and a pressed tint in dark goes darker rather than nearer the primary for the same reason. Its primitives are shadcn/ui's Base UI components, copied into `web/src/ui` and owned here: the shadcn CLI generated them in a scratch project rather than in this repository, where it would rewrite the stylesheet and install unpinned versions, and a `hunk:` comment marks every change from upstream. Those changes map them onto the type scale, the radius steps and the base layer's 2 px focus outline, and tell a selected tab or pressed toggle by a 3:1 border as well as its fill. Base UI, cva, lucide icons, Sonner and react-resizable-panels come with them. Tailwind, its native compiler and these libraries are build tools or bundled into the UI, so the package still installs with no dependencies.

The review components are in `web/src/review`, on the domain's own `FileChange` and `Hunk`, and the pages are built from them: the hunk card a part shows in, with its unchanged callers and line comments; the file tree, which is also the rail beside the code; the mechanical changes; the line of keys under a comment box; banners, empty states and skeletons. A diff viewer, the PR header, a comment composer and a publish panel are there for what the pages don't use yet. The review thread, with its suggestion diff, is in `web/src/review/thread`. The PR's state, review status, CI and reviewers are in `web/src/review/pr`. A command palette waits for a feature that needs it. The UI's own CSS before it, a token file and a stylesheet per page, is gone: everything is the design system's utilities.

- **The diff is an ARIA grid.** The grid takes the focus and points `aria-activedescendant` at the focused line, so ↑ and ↓ move it and ⇧ extends a selection, even past the rows drawn: a file over 300 rows draws only those in view, with TanStack Virtual. Every changed line says "added line 20" to a screen reader as well as having its marker. Biome's rules that want native elements and focusable rows are off for `web/src/review/diff`, since a grid's rows are neither.
- **Syntax colors are tokens.** Shiki's CSS-variables theme names each token's scope, and the scope picks one of the seven `--syntax-*` colors, so code follows the theme and the contrast check; the GitHub themes used before brought their own hex values. The theme's scopes fit TypeScript's grammar, so Java's are mapped on top of it: its grammar calls every type `storage.type` and every receiver `variable.other.object`, and a line of Java read as keywords and numbers. A type is plain wherever it's used, as IntelliJ and GitHub show it, and what a declaration declares and a call are the function color: the grammar names a type only in some places, and coloring those made one type two colors and a signature one color with its method's name. UPPER_CASE constants take the constant color, as on GitHub, through a small injection grammar, since Java's names them nothing, and annotations the decorator color; a call's arguments are plain, where its scope covered them. Coloring types as functions was the version before, and reviewers still found Java hard to read. Most of that was where a hunk starts: each side of a hunk is highlighted alone, and Java's grammar reads a method declaration only in a class body and a statement only in a method's, so in a hunk every signature read as a call, `throws` plain. A Java side now starts in the state its first line is in, guessed from its indentation and its first words (a modifier or an annotation is a member, a keyword or an assignment a statement), with a block opened for each level deeper; a whole file starts at indent 0 and is read as before. Highlighting the whole file for every hunk was the alternative, a request per file before any color. TypeScript's grammar has the same trouble with a class's methods, and is left until someone reviews classes in it. A theme of our own for every language was the alternative to mapping, and would recolor the languages that read well. Word changes come from the review module's own word diff rather than jsdiff.
- **The palette is IntelliJ's, without the hues that mean something here.** Green, red and amber are added, removed and severity, so no token takes them: strings are teal, keywords and numbers blue, functions a blue-green, decorators and attributes purple, and everything else, types among them, the text's color. Violet keywords and amber constants were the version before, the amber from before amber was a level. Two roles are mapped on top of the theme's five, in every language: a decorator or annotation, by its name and its `@`, and an attribute, a tag's or a keyword argument's name. Java's annotations took the constant color before; that's the number color, now a blue beside the keywords' blue, where an annotation over a modifier would read as one. For the same reason receivers, declared constants and built-in types, which the theme colors as constants, are plain in every language, as Java's receivers already were, and a primitive type is a keyword: left as they were, half the names on a line of TypeScript were the number's blue. That recolors languages that read well, on that one rule, and the constant color is left to literals, `this` and Java's UPPER_CASE names. The design's own Shiki themes, a hex per scope in light and in dark, were the alternative: a theme of our own for every language, with colors outside the tokens and the contrast check, and types plain and tags keywords in languages nobody asked about. In dark the design's hues are lifted in lightness to 4.5:1 on an added word's `#286142`: drawn for a near-black page and its darker word tints, they stand at 3.4:1 on ours, and its dimmer base text would then be no brighter than a comment, so code's text stays the foreground. Its dark diff tints were left where the dark surfaces put ours; in light its line tints, a little quieter, and its word tints, a little stronger, are taken as they are. A line's number keeps its line's green or red, where the design has grey: grey is 3.3:1 on our dark added gutter. The design asks for a whole file to be tokenized before it's split into lines; a side still starts in the state its first line is in, for the reason above.
- **Code and the tree have faces of their own.** Code, line numbers, hunk headers, code in comments and the tree's counts are JetBrains Mono, code at 13.5/22 and its line numbers at 12.5, in one weight: review is mostly reading, and it tells `0` from `O`, `1` from `l` and `rn` from `m`. Its ligatures are off through `calt` as well as `liga`, since it draws `=>` and `!=` as contextual alternates, and a reviewer reads every character as typed. The tree is Inter, names at 13.5 px and weight 500 in 30 px rows with a 14 px indent, directories at 12.5 and counts in the mono at 12: a proportional face fits more of a name into the rail than a mono does, and the larger size cuts names more often, which the middle cut already handles. The header, the bar, a file card's path and key hints keep Geist and Geist Mono, as the header's design has them. Geist Mono at 13/20 for code, and the tree in Geist at 13 px in 28 px rows with a 9 px indent, were the version before. One mono for the whole page was the alternative, a font fewer to load; the header was drawn in Geist Mono and the code beside it in JetBrains Mono. Both faces come as fontsource's variable packages, as Geist does: they bring the Cyrillic, Greek and extended Latin a comment or a string can hold, each subset fetched from the local server only when a glyph needs it, and their licenses reach the package's notices with the rest. The static Latin files in the design's archive were the alternative, and would leave a Cyrillic comment in the system's mono. No font is preloaded, which the design asks for: the files' names are hashed at build, and a mono swapping for a mono barely moves a line.
- **One keymap.** `web/src/lib/keymap.ts` lists every shortcut once with its keys: the diff grid's arrows, ⌘↵ to send a comment or open a link in a new tab, and Esc; handlers and the line of keys under a comment box read it. A key without a modifier never fires while typing. There are no letter keys, so none for speech input to type by accident (WCAG 2.1.4); a switch to turn them off was in the `?` dialog while there were.
- **A color that fails moves the element, not the token.** The tree's status letters were 4.43:1 on `accent` (M in amber), so the active row went to `surface-subtle` with a primary bar. When dark cards went flush with the page, `surface-subtle` went with them and the active row lost its fill, leaving only its bar; the tree's rows have their own `surface-row` now, `#262626` in dark, and the check fails a row fill that matches the page or a card. v4's hover on `accent` put a deleted file's red at 4.43:1 in dark, so a hovered row is `surface-row` too. The contrast check covers each pair the components use. A changed word can't move: it's any token on the added or removed tint. So the check covers every syntax color on every line and word tint, and in dark every hue is lifted to 4.5:1 on an added word's `#286142`; three were 3.95–4.15:1 when only three sample pairs were checked.
- **A line number is an inline target.** The number that opens a line's comment box is a 48×22 px button, as tall as its line of code, so two consecutive lines put their buttons closer than 24 px. WCAG 2.5.8 exempts a target whose size the line height of its text sets, as it does a link in a sentence. The button says so with `data-inline-target`, and the target check exempts it only while it's no taller than its row's line height. Rows of 24 px were the alternative: less code on a screen, 17% less when rows were 20 px.

The design system has a page of its own, `/design-system.html`, served by `pnpm dev:web` and left out of builds. It replaces the dev-only playgrounds the old styles had, and shows the tokens live (swatches, type, spacing, radius, elevation, motion), every primitive and component in its states, and three screens put together from them, all on made-up data and switchable between light, dark and the color-blind diff. Playwright checks it in all four combinations of theme and diff palette (`e2e/design-system.spec.ts`): Chrome's accessibility tree for names, then in the page ARIA references, ids, text contrast as rendered and 24 px targets; a Tab walk that wants a 2 px outline on each stop and no trap; the keyboard map on the mock screens; reduced motion; and screenshots, compared on macOS only, since fonts render differently on each platform. axe was the plan and isn't used: it's MPL-2.0, outside the licenses this repo takes, so the checks are our own and narrower. A test plants one of each problem to prove they're caught. Mapping Indigo Calm's values onto the plain CSS tokens was the alternative, smaller and with no new dependencies; Tailwind was chosen to take the design system whole, with its components and contrast check, instead of keeping a translation of it.
