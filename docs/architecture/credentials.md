# Credentials

| Service | Source | Required |
|---|---|---|
| GitHub | `GITHUB_TOKEN`, else `GH_TOKEN`, else `gh auth token` | For GitHub PRs |
| Bitbucket Cloud | `BITBUCKET_EMAIL` + `BITBUCKET_API_TOKEN` (scoped Atlassian API token), else `BITBUCKET_USERNAME` + `BITBUCKET_APP_PASSWORD`; `BITBUCKET_WORKSPACE` for the picker and to learn who the user is | For Bitbucket PRs |
| Claude | Claude Code's own sign-in, through the `claude` on the PATH; else the SDK's resolution: `ANTHROPIC_API_KEY`, else an `ant auth login` profile | For Request AI review, which says why it can't run without either |
| OpenAI | Codex's own sign-in, through the `codex` on the PATH | No. Without it, OpenAI's models are listed, disabled, in Request AI review's menu |
| opencode | The providers the reviewer connected in their opencode, through the `opencode` on the PATH | No. Without it, its row in Request AI review's menu is disabled with the fix |
| Jira | `JIRA_BASE_URL`, `JIRA_EMAIL`, `JIRA_API_TOKEN` | No. Without it, ticket keys are shown but not fetched |

Bitbucket app passwords are accepted because existing setups for other tools often have them, and both kinds are the same Basic auth to the adapter. Atlassian removed app passwords in July 2026, so `doctor` points to an API token when one is rejected; rejecting them outright at startup was the alternative.

megareviewer never reads Claude Code's credentials: it runs the unmodified `claude`, which signs its own requests, and removes `ANTHROPIC_*` and `CLAUDE*` variables (but `CLAUDE_CONFIG_DIR`) from its environment, since an API key there would make Claude Code bill the API while the startup line says the plan. Claude Code can run the passes when it's installed, signed in and no older than the version megareviewer was checked with, and the API when the SDK finds credentials. Each is a provider of the model options the reviewer chooses from (see [Model passes](model-passes.md)); both are asked at once whenever the status is, 5 seconds each, so a hung `claude` can't hold the page. One that can run is kept for the process; one that can't is asked again on the next status request, so signing in to Claude Code needs no restart. Without a choice, a run uses the option the last model call used, while it can run, else Sonnet 5.5 on Claude Code when it can, else on the API, else GPT-6 Sol on Codex, else opencode's own default model. Claude Code only was the alternative: it would break the model for everyone set up with a key. A flag to force one, `--ai-via`, went with `--ai`.

Codex is to a ChatGPT plan what Claude Code is to a Claude plan, and is the third provider, after both of Claude's. megareviewer never reads its credentials (`~/.codex/auth.json`): it runs the unmodified `codex`, and removes `OPENAI_*` and `CODEX_*` variables (but `CODEX_HOME`) from its environment, since `CODEX_API_KEY` wins over the ChatGPT sign-in. `codex --version`, `codex login status` and `codex debug models` say whether it can run, whether it's on a plan ("Logged in using ChatGPT") or an API key, and which models the account has. The OpenAI API with a key was the alternative; it's the one way to run OpenAI's models with no tools at all, but it can't spend a ChatGPT plan, and it's left for when someone asks.

opencode is the fourth provider: one command in front of whichever model providers the reviewer connected, local ones among them, so every model it can reach is an option without megareviewer learning each vendor's API or holding a key. megareviewer starts one `opencode serve` of its own on the first status request, on 127.0.0.1 at a port it picks, with a random password, in a new empty directory, and stops it on close; one that dies is started again on the next use. It never reads opencode's stored credentials: `opencode --version` says it's installed, and the server's `GET /api/model` lists the models its providers offer. The reviewer's opencode config is read, since that's where providers are defined, but not the project's or Claude Code's, and opencode's own free models are left out (`OPENCODE_DISABLE_FREE_MODELS`): they run on opencode's inference service, which the reviewer never connected. Pointing opencode at an empty config directory was the alternative; it would hide every provider configured in a file, which is how local models are added. Attaching to an opencode server the reviewer already runs was the other: megareviewer starts its own, so it knows the config it runs under. 2.3.0 is the first version whose server megareviewer speaks; an older one isn't started.

At least one git host must be configured. Credentials stay in the server process and are never sent to the browser. The hosts' are also what megareviewer's own copies are downloaded with (see [megareviewer's own copy](local-checkout.md#megareviewers-own-copy)).

## Local server security

- Binds to `127.0.0.1` only.
- The CLI creates a random session token and opens the UI with it. Every API request must carry the token, and the server checks the `Host` header. This stops other web pages and DNS rebinding from reaching the API.
- The page takes the token from the link's `?token=`, takes it out of the address bar at once with `replaceState`, and keeps it in `localStorage`, so every tab and window of that browser has it: a PR opened with ⌘-click, a middle click or Open link in new tab, and a review's URL pasted into a new window. It was `sessionStorage` first, which is a tab's own: a new tab started without the token and asked for the terminal's link. `localStorage` is the origin's, `http://127.0.0.1:<port>`, where only the server's own scripts run (`script-src 'self'`), so no other page, nor a rebinding name, which is an origin of its own, can read it. A stored token outlives its server but not its use: every start makes a new one. With the default port 0 every start is a new origin as well; with a fixed `--port`, a tab left open across a restart has a request refused, then takes the token a newer tab stored, and asks for the link only when there's none. The events and attachment routes keep the token in their query: those URLs never reach the address bar, and `Referrer-Policy: no-referrer` keeps every URL out of a `Referer`. An HttpOnly `SameSite=Strict` cookie set by the link was the alternative, and would take the token out of those queries too: but a cookie is the host's, not the port's, so every other server on 127.0.0.1 would receive it, and to SameSite every port of 127.0.0.1 is one site, so a page of any local dev server could send requests that carry it, which the custom header rules out without an origin check. Handing the token over was the other: `window.open` misses middle clicks, the context menu and pasted URLs, which the page never sees, and a BroadcastChannel to a tab still open fails once the last one is closed, and makes every new tab wait for an answer.
