# Review threads

The PR's existing threads are on the code they're about: under their line in the file's card, or, when the code has changed since or no part shows the line, under "Earlier comments" at the bottom of the card, with the line they were on. A thread on a file without a card goes in a list after the cards. None is dropped. A thread sits in the same card as a draft, with a bar apart from its edge in its state's color, draft, open, resolved or outdated, and says the state in words too; a 3 px border on a thread and a flush row for a draft were the first version. Consecutive comments by one person share one header, their initials and name, an Author chip for the PR's author and how long ago, with a rule only between people. The text lines up with the name, every time sits at the right, and a line under the initials runs down a run of several: three replies in a row by one person read as three paragraphs of one comment without it. A time and a hairline at the start of each later comment was the first version, and looked like a heading cutting the run. A full header on every comment was rejected, three identical headers for three short replies, as were a tinted block per comment, boxes inside the thread's box around a suggestion's box, the times alone in the gutter, and a dot on the line at each comment. A thread opens with a line naming its lines and counting its comments, "Line `R16` · 2 comments", with its Outdated and Resolved marks. It ends, lined up with the comments' text, with what looks like a field, "Reply…", and Resolve with a check beside it, so writing a reply and resolving don't read as two buttons of a kind. A row of outline buttons, Reply, Add to batch and Resolve, was the version before; the three looked alike. A click on the field opens the real one in its place, under a rule, with "⌘↵ reply · Esc cancel" under it, and the field stays while it has text, is posting or has failed. A Reply and resolve button was in the design and was left out: one more button for two clicks that already exist. A field always open was the first version, and made every thread a reply box taller. A resolved thread folds to one line saying who resolved it. The tree's rows and the cards' headers count each file's open threads. A thread has no keys of its own: its field and button are the way to reply and resolve, and only the comment box keeps its keys, ⌘↵ and Esc. `r`, `e` and `b` with the focus in a thread were the first version; the thread took the focus as a tab stop for them, and their hints on every button were noise beside the button's word.

**Going round the threads.** The bar's pager goes round the PR's unresolved threads as it goes round Claude's findings, with the same parts but Start: before the first step a speech bubble, the count and how many files they're in, "3 unresolved in 2 files ▾", in grey, since a thread has no severity, which opens the list, where the reviewer picks the thread to begin at; on one, Previous and Next, the current thread's opening words, "Sam Ortiz: Say the charset…", which go back to it, and a position that opens the list of them in the same popover as the findings'. Before Claude runs, while it reads and when it found nothing, the pager is the threads', after Claude's slot; once there are findings, the threads are a chip after the pager, "3 unresolved" with a speech bubble, a toggle that has the one pager walk them, so the two never take the row's room twice. Start, as the findings' pager has, was the version before; it went at the reviewer's ask, and Start is the findings' alone. A second pager beside the findings' was the alternative: two titles on a row that never wraps, both cut to nothing below 1280px. Going to a thread, from the list too, keeps the pager on the threads, after Claude's run lands as well, and going to a point takes it back to the points; only what it's on has a ring. The steps are the unresolved threads in the page's order, top to bottom: the files in the tree's order, in each its threads by line, then its earlier comments, then the threads on files without a card, so Next never goes back up the page. The host's order was the alternative, and on the fixture PR it put line 32 before line 29. A resolved thread is never a step nor in the list, grouped by file with the current thread marked: it's a conversation that's over, folded on the code where it was. A thread the reviewer resolves on the page leaves the steps once the threads are read again after the write; from it the pager keeps Previous and shows the count in the title's place, and Next and Previous go to the nearest step down or up the page; a reply changes nothing, and a comment posted now is a new step in its place. When the last one is resolved the chip goes and the pager is back on Claude's findings, or gone. The version before kept a thread resolved on the page as a step, marked with a check, went round all the threads once every one was resolved, and had Unresolved and All in the list: the reviewer stepped through conversations nobody had left to answer. Going to a thread scrolls it under the bar and its file's header with the lines it covers above it, gives it the focus, rings it, and opens it if it's folded; from the overview, which shows no threads, it opens the map. A screen reader hears the position, the file and the line: "Thread 2 of 3, src/services/receipts.ts line 29: Lee Park: Name says what it counts." The reviewer's drafts aren't steps: they're their own words, and Publish lists them with their lines. The header's count stays text, since the bar under it says the same and stays in view. There's no key for it, as there's none for the points: many PRs have no threads, and the buttons are on the bar on every screen. A PR without unresolved threads has no thread pager.

A suggested change shows as a small diff: the lines the thread covers, as the map shows them, and the suggestion's lines. It's read here and applied on the host. Applying them was the version before: Add to batch on each, then "Apply N suggestions" in the header made one commit on the PR's branch through the host's API, on the analysis's head or nowhere. It took a button on every suggestion, a dialog, a route, a commit write per host and a read of the reviewer's push permission, for what the host's own page already does.

How threads work, and what was rejected:

- **Read live, not cached.** Threads change without a push, so caching them by head SHA, as analyses are, would show stale ones. They load when the page opens and again after each write. A failed read is a warning above the code, never a failed page.
- **A port of their own.** `ReviewThreads` (`getThreads`, `reply`, `comment`, `setResolved`, `getAttachment`), not four more methods on `GitHost`: publishing a review and taking part in a conversation are different use cases, and both adapters pass one contract suite.
- **No severity on comments.** Hosts have none, and megareviewer adds none: a comment's words say how much it matters. Only a finding of Claude's not yet added to the review shows one, as Claude's. A severity of our own on comments was the version before, written into the body as `**minor:**`, `**major:**` or `**blocking:**` and read back from it as a chip; a body that still starts with one shows it as the bold text it is.
- **Suggestions in the host's format,** a ` ```suggestion ` block, which GitHub renders natively, so a suggestion reads the same on either side. One that doesn't close, holds a fence of its own length or is one of two in a comment is shown as text or code. An empty one deletes the lines.
- **Bodies are untrusted.** A parser of our own reads the Markdown review comments use, and the page builds elements from what it reads: no `dangerouslySetInnerHTML`, and HTML in a body stays text. Blocks are paragraphs, headings, quotes, bulleted, numbered and task lists, tables, rules, fenced code (colored like the diff) and suggestions; inside them, bold, italics, strikethrough, code spans, links, backslash escapes and entities. A heading is bold text, not a heading of the page. A suggestion is read only at the top of a body, never quoted or in a list. Quotes, lists and emphasis nest 8 deep and the rest is text, and the parser reads no string twice per level, so a body built to exhaust it can't. Paragraphs, code spans and fenced code alone was the first version, and Bitbucket's comments read wrong in it: its editor writes Markdown and escapes every underscore and bracket, so `AWS\_KEY` and `\(maybe\)` showed their backslashes, `**bold**` its stars and a list its bullets, in 70 of the 178 comments on 27 PRs of four of Atlassian's public pipes.
- **Links are links, to http(s) only.** A link opens in a new tab with `noreferrer`, underlined so color isn't its only mark, its URL in its title; one to another scheme, or a relative one, is its text alone. Bare URLs and `<url>` are links, as on both hosts. Every link as text was the version before, so a PR author couldn't learn who's reviewing; but that's what fetching does, and the page still fetches only the host's attachments. A link is followed only when the reviewer clicks it, as a check's Details already is, and as text the reviewer had to copy out the ticket or docs a comment pointed to.
- **Bitbucket's mentions are named.** Its editor writes a mention as `@{account_id}`, and the adapter writes the person's name instead when one of the PR's comments is theirs; any other stays as written, since naming it would cost a request per person. The `{: data-inline-card='' }` the editor writes after a link it shows as a card is dropped.
- **Attachments through the local server.** An image pasted into a comment (an `<img>` tag or `![alt](url)`), or a video (GitHub's attachment URL alone on a line), shows in the thread when it's in the host's own attachment store: `github.com/user-attachments/assets/…`, GitHub's user-images hosts, a Bitbucket repository's `/images/`, or a file in a Bitbucket repository by its `/raw/{ref}/{path}` URL, which the server reads from the API's `src` at that ref, since the site answers a token with its sign-in page. The page loads it from `GET /api/analyses/:id/attachment?url=…`, which takes the token in the query as the events route does, since `<img>` and `<video>` can't send headers. The server fetches it with the reviewer's credentials, sending them to the host's own origin only and following its redirect to signed storage without them, and passes on only PNG, JPEG, GIF, WebP, AVIF, MP4, WebM and QuickTime up to 25 MB. It answers byte ranges, which a video player asks for to seek; without them a video only played from the start. A click on an image opens it over the whole window, and Esc, its close button or a click beside it closes it; a video has its player's own full-screen button. An `<img>` tag's `width` and `height` go to the page, so the image keeps its place while it loads and the code under it doesn't jump. The last 100 MB of attachments stay in memory, newest kept, since a player asks for one in many ranges and an attachment's URL names its content; an SVG could carry scripts into this origin. Any other URL is a PR author's choice and is never fetched, so it can't tell them who's reviewing: it's named by its alt text. Loading images straight from their URLs was the alternative; the CSP's `img-src https:` would allow it, but a private repository's attachments need the reviewer's credentials, videos need `media-src`, and a tracking pixel would load too. Showing an image's raw tag was the first version, then naming every image without loading it; on delphi-code #2 the reviewer wanted to see the screenshot. A Markdown library with a sanitizer was the alternative; it's a dependency and HTML to get right, for features a review comment doesn't need.
- **Initials, not avatars.** Avatars would load from the host's CDN for every comment, a request per face that tells the host who's looking, for a picture the name already gives.
