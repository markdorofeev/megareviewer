# Review page

It opens on the code. The header names the PR once: its title, its number after it in grey, a link to it on the host, then the PR's state and its review status, and at the row's other end its CI and reviewers; one muted line of its repository, how much of it was read, who wants to merge which branch into which, when it was updated, and the lines it adds and removes, counted once the diff is read, a zero left out; and its intent as one line: what the change does. A line of the repository and number above the title, a count of threads beside it and the files in the byline were the version before: the bar's thread chip and the tree's file count said them again. Once Claude has run, a status line opens the brief, "✦ AI review · Sonnet 5.5 through Claude Code · latest commit", or "new commits since"; while it runs, "AI review running" and how many of the run's passes are done, three with the tour and two without, with a bar. It says only where the brief comes from: what can be done about it is in the bar. Its lead is semibold in the text's color, and only the check of "Does what was asked" is green; a green lead and a muted one were the version before, and read as two levels. It's Claude's once it has run, with the code names it writes in backticks set as code, as text, never as HTML. Before, it's the description's first sentence, with its Markdown markers dropped as plain text. Three lines were the version before: the run's Through and Watch under its summary, and before a run the code's own, from the overview's directories and the unchanged callers (see [docs/design/intent.md](../design/intent.md)). An info button, Details, ends the first line and opens the full intent in a dialog. The header scrolls away with the code.

**How much of the repository was read** is an item of the byline, after the repository's name, once the code's stages are done: before that an analysis about to download says `none`, which would read as PR only for the seconds until the download starts. It's the analysis's `checkout` in three forms, each an icon and words: Whole repository for `read`, Downloading repository… with a spinner for `downloading`, and PR only, in the text's color and medium weight, for `none`, `missing-commit` and `download-failed`. It opens a popover. Read, it says how many uses outside the PR were found, tests among them, then the head commit and whether it was the reviewer's clone or megareviewer's own copy, its folder in a tooltip: "26 uses outside the PR. Read at `73432ec` from megareviewer's copy." A sentence naming the repository and the folder was the version before, three lines in the popover where the count, what the reviewer opens it for, came last. Otherwise it's the note the Details dialog ended with before, which a reviewer had to know was there: that it's downloading, or why nothing was read and what would fix it, now also that the repository wasn't downloaded because of `--no-download`. The status response's `downloadFolder`, the folder copies are downloaded to or null when that's off, tells a copy from a clone and says whether downloading is on; a folder under it is megareviewer's own. With downloading off a copy already there is still read, and is then named as a folder like any other. [docs/design/reading-the-code.md](../design/reading-the-code.md) says why it always shows, and why not in the bar.

**Where the PR stands** is read live from the host, as threads are: when the page opens, when the window is back in focus, after a publish, and every minute while a check is running and the tab is visible. It changes without a push, so it isn't part of the analysis, and polling is kept to that minute since a host's rate limit is shared with the rest of the tool. A port of its own, `PullRequestStatusSource`, reads it, apart from `GitHost` and `ReviewThreads` for the reason threads have theirs.

- **The state badge always shows:** Open, Draft, Merged or Closed (Declined and superseded on Bitbucket), with an icon. Showing it only when a PR isn't open was the alternative, since nearly every PR reviewed is, as nearly every file is modified and the tree shows no status for those; but the header names one PR, not a list of rows, so one badge costs little, and one that's always there is learned, so its change to Merged is noticed.
- **The review status shows only when it says something:** Approved or Changes requested. GitHub's own `reviewDecision` is used, since it counts what branch protection counts, and where it has none (a repository that requires no review) and on Bitbucket it's derived: changes requested if anyone requested them, else approved if anyone approved. "Review required" is every PR waiting for this reviewer, so it isn't shown.
- **CI is the analysis's head commit's,** not the PR's latest: the reviewer reads the code at that commit, and a pass on a newer push would vouch for code they aren't looking at. One line, "✓ CI 12/12 passed", "✕ CI 2 of 12 failed", "◌ CI 3 of 12 running", opens the checks, failed first, each with a Details link. Skipped checks don't count toward the total. A check's link is a URL a CI integration set, not a PR author, so it's a link, but only http(s), and with `noreferrer`. A change of the line after the first read is announced politely. Checks the token can't read say so, with the scope to add; a commit without checks shows nothing.
- **Reviewers are initials,** as in threads, each with a mark of its verdict (✓, ✕, a speech mark for a comment, none while only asked), changes requested first. Three at most, or two and `+N`. They open a list with each verdict in words. The PR's author isn't one.
- **The bar gets none of it.** The design's compact header repeated Changes requested; the bar's one row is the pager's, and the PR's state doesn't change while it's read.
- **A read that fails is quiet:** "Status unavailable" where CI and reviewers would be, opening why and Try again, never a failed page.

Under it is the **bar**, one 52 px row that stays at the top of the window: the switch between the layouts, Claude's slot, Show files at 1024px or less, the reviewer's verdict on the host, then Approve and Publish. Once it's stuck it names the PR by its title, between Claude's slot and the reviewer's verdict. From 1280px the bar keeps 160 px for it, stuck or not, so the pager is one width either way; below, the title shows where the room nothing else needs is at least 128 px. The title only in that leftover room was the version before, and there was none at 1280px, nor at 1440px beside the threads' chip. The title first, up to 384 px and a divider, was the one before that: it came in as the first step scrolled the page, and moved the pager some 200 px from under the pointer, and at 1280px it left a finding's title a few letters. Each color in it means one thing: the primary as a tint is AI, filled it's committing a review, green is approving, red, orange and amber a finding's severity, and the rest is grey; at most one button is filled. `barButtons()` decides which: Publish while line comments wait for it, with their count; Approve once Claude's run is done and nothing waits, last on the row, unless the reviewer already approved or requested changes; neither before then, when the AI's tint is the row's strongest thing. Approve approves at once, with no dialog (see [Publish](ui-publishing.md)). On the reviewer's own PR it's disabled, focusable and says why. New commits since the analysis don't disable it; it stays in outline then, beside Re-analyze's stronger tint. While the reviewer's approval stands it's Revoke approval instead, in outline and never disabled, and Publish shows only while comments wait. The verdict before the buttons is the reviewer's on the host, ✓ Approved, ✕ Changes requested or a speech mark and Commented, linking to the latest review published from the analysis when there is one; the PR's status says each reviewer's verdict, and the analysis view carries the reviewer's ID on the host (`currentUserId`) to find theirs. What the reviewer just did, an approval, a revocation or a review, sets it at once and holds until the status read after it answers, so the bar follows the click rather than a read that can fail (`verdictAfter`: a comment leaves an earlier approval or request for changes standing, as both hosts count them). The page opens on the code because the intro in front of it, an intent panel and two sidebars, was what reviewers skipped. Two alternatives were rejected:

- A path of questions, one per concern, which put the intent and a question before every piece of code.
- One tour step at a time beside sidebars for the tour and the decisions. It split the reader's attention across three panels. It was the first version.
