# Layouts: map, tour and overview

The layouts the review bar's switch goes between, described in [ui-review-page.md](ui-review-page.md):

- **Map**, the default: every changed file once, in one scroll, then the proved-mechanical changes, beside a rail of the files, as a tree. The files are in path order, as a directory tree lists them: at each level directories before files, then by name. A file is one card with all its parts in the file's order, mechanical ones collapsed in place with their proof. The card's header names the file after its type's icon, as the tree has it, its directory muted before its name, a new or deleted file's name in its status's color and a renamed one by its old path and a chip, and the lines added and removed. A part shows no risk class of its own. A bar beside each part's lines, colored by its risk, was the first version; a count of contract parts in the header, with the path rules' reasons, came next, and went when contract became internal (see [Deterministic prep](pipeline.md#2-deterministic-prep-no-model)). A part has a divider only to say that it changes a definition used outside the PR, "Used unchanged in 2 places and 1 test", opening each use with its file, line and the lines around it. When the callers come after the page opened, their dividers go in as a guardrail call's marks do (`useMarksHeld`): the line of code at the top of the window is held, and no landing plays. A rule's reason on the divider was the first version; it quoted the lines under it, the name a part defines and the route it declares, and said which rule fired rather than anything about the code. Keeping only reasons the screen doesn't show came next, such as the file a credential call lands in; that was still a guess from a name, readable in the code. The unchanged lines between two parts, above the first and below the last are a subtle fold, an unfold icon and "17 lines unchanged", and a click on it opens all of them, shown as the parts' unchanged lines are. Buttons for 20 lines from either end and for all of them were the first version; they put three controls on a row that one click does the job of. Below the last part the count is known only once the file is: a hunk with fewer than git's 3 lines of context after its last change, or no newline at its end, reaches the end of the file and has no fold. The first fold opened fetches the file at the PR's head commit from `GET /api/analyses/:id/files/:side/:path`, which serves only the PR's own files and reads them from `file_contents`, where Collect left them, before the host. Fetching every card's file as it came into view was the alternative; it would show the count below the last part at once, at a request per file the reviewer may never open. Only a file in both commits has folds: an added or deleted one is whole in its diff. A card's lines scroll sideways as one, its parts and opened folds together, with its dividers, fold rows and comment boxes held at the visible width; a scroll per part was the first version, and a part with a long line scrolled away from the lines around it.

  The tree beside the code says where the code being read sits in the codebase: directories are the one part of its structure known without a checkout. It's drawn as the `hunk-filetree-v4` design has it, which took IntelliJ IDEA's project view for its model, since that's the tree the Java reviewers it was drawn for read all day. Every directory is a heading, a chain of directories with no files and one directory in it is one heading (`web/src`), and at the top a directory with no files and more than one directory in it is no heading, so it costs no indent on every row under it. Two or more headings in a row under such directories are a group: a muted caption says the directories once, `src/test/java/com/acmecorp/fulfillment/orders/`, and the headings under it, a level in, name only what's below it, `controllers` and `services/payment`. A heading alone keeps its whole path, as `substratevm/src/com.oracle.svm.core`, and stays at the top level, so it doesn't read as one of the group above it. Those directories before every heading's name was the version before: on the Java service fixture four headings began with the same 46 characters, wider than the rail, and its end, where they differed, was cut off. A heading or a caption too long for its row loses whole directories from its middle, `java/com/…/fulfillment/orders`, measured as a file name is. On the many-folder fixtures that's 2, 2 and 7 captions. A Java module's sources repeat its name, `com.oracle.svm.core/src/com/oracle/svm/core/pgo/`, and the tree leaves the repeat out, `com.oracle.svm.core/pgo`, the full path in the row's tooltip; `byTreePath` compares the paths as the tree shows them, so the cards keep the tree's order. A heading is a chevron, its folder's icon and its path, muted with its last directory in the text's color and medium weight, and a closed one says how many files it holds. Headings don't stick and have no guide line. The version before v4 had both, gave a directory of one file no heading, its row naming it (`routes/setup.tsx`), and said the directory every file is in once above the tree; on the many-folder fixtures that was 13, 9 and 22 headings for 24, 23 and 27 files, and v4's rules make them 18, 20 and 22. Before that, headings outnumbered files (23 for 24, 25 for 23, 35 for 27), and a flat list with a heading per directory had seven headings for delphi-code #2's seven files.

  The icons are IDEA's own New UI ones, unmodified, light and dark variants, vendored in `web/src/review/tree/icons/` with their Apache-2.0 license and provenance and listed in the package's notices: a Java file is a class, a Java test a class with IDEA's test mark, a deleted Java file Java's file type, since there's no class left, and other files their type's icon, `unknown` when IDEA's set as vendored has none (CSS, HTML, Go and others for now). A directory is a module when it's a dotted name with a `src/` in it, a package inside one or under a Java or Kotlin source root, else a folder. Every Java file shows the class icon: an interface's or an enum's would need prep to record each file's top-level type from tree-sitter, a contract change and a pipeline version bump that drops every cached AI run. Each icon is two images, the dark one shown under `.dark`, so the theme switches without a render; they're images rather than markup because their colors are the icons' own, which the tokens rule keeps out of our source. They carry no status, so the contrast check doesn't cover them. Lucide shapes by role, colored by language family, with a file-plus or file-minus for a new or deleted file, were the version before.

  A file's status is on its name, as IDEA colors changed files: a new file's name in the added lines' color, a deleted file's in the removed lines' color and struck through, a modified or renamed one in the text's color, and a new or deleted file's extension a muted mix of its color. A rename says "was" and its old name in the tooltip, and the row's accessible name says the status in words, with its type, lines, threads, findings and directory. On screen a new file is told from a modified one by its color alone, which in dark is 1.02:1 against the text, below the 3:1 WCAG 1.4.1 asks of a difference in color alone; the design was taken as it is, over ENGINEERING.md's rule that a status is never color alone, and so was the rename, which only the tooltip shows: the `renamed` chip was the version before. A file's row is its icon, its name and its marks: open threads, a dot in `severity-minor` for Claude's findings with their count above one, and its added and removed lines, a zero left out, in tints mixed toward muted. The dot is the design's, whatever the finding's severity; the design's ring for a risk went with the risks. A row never wraps: a name too long for it loses whole camel-case words from its middle, `Recurring…Support.java`, never its extension, measured with a canvas in the row's font whenever the rail's width changes; the version before wrapped the counts under the name, a line taller.

  The filter at the top narrows the rows by path, and All and Findings beside the file count narrow them to the files with a finding, with how many there are. The tree is one ARIA tree and one Tab stop, the row last moved to or else the file in view: ↑ and ↓ move between rows, ← closes a directory or goes to its heading, → opens one, Home and End, Enter and Space select a file or toggle a directory, ↑ from the first row goes to the filter and ↓ from the filter back. A button per row, a Tab stop each, was the version before. The file in view, the last card whose top has passed a quarter of the window, is the selected row, on `diff-hunk-bg` with a 2 px primary bar, and when it changes the tree opens the directories down to it, leaving the others as the reviewer set them, so a directory the reviewer closes stays closed until another file in it comes into view; a click on a row scrolls to its card. At 1024px or less the tree is behind a button. The rail before it showed a bar per part, with its lines and risk, and only each file's last path segment: two `hosting_services.py` on delphi-code #2 read as one, and a row per part said what the cards say again.

  Two ways to show how the file in view connects to the others were tried beside the tree and removed, because links between files didn't help while reviewing: arrows on the rows of the files that call it and that it calls, with the other rows muted, and a `Tree · Overview` switch at the top of the rail whose second form was a miniature of the overview, its boxes scaled to the rail with the current directory's files and neighbors listed under it. The bar's switch opens the full overview.

  The page was cut back to these primitives, to be rebuilt only from what proves useful. Each removed element added text without helping the reviewer:

  - the rail beside the code, with a bar per part, its totals and its Show Map button, since rebuilt as the tree;
  - the grouping switch (call order or folders) and call order itself, which the overview still shows;
  - the contract index above the code, and the "Contract changes only" filter;
  - the jump palette (`⌘K`, `t`) and its field above the code;
  - calls opening in place, call chips and peeks, and the divider's links to callers in other files; a call's code is back as a card on hover, without chips (below);
  - reviewed marks (`x`, `[`, `]`), with the dimmed bars and ticked files that showed them;
  - `j` and `k` between parts;
  - the letter keys, `n` and `p` between files, `c` to comment, `o` for a call's code, `u` for a split diff, `v` between the layouts, `/` for a filter, ⇧R to publish and `?` for a list of them all, with its switch to turn them off: each did what a button, a click or Tab already does, and their hints on buttons and in tooltips were text the page didn't need.

  A call into code the PR changes shows that code where the call is. Its name has a dotted underline, solid under the mouse, and resting on it for 300 ms opens a card under it: each part that changes the called definition, as the map shows it but numbered by the new side only, since the base's column is empty beside every added line, opened at the line that defines the name, under its file, lines, counts and "Go to file", which scrolls to the part. The card stays open while the pointer is on the name or on the card, and closes 150 ms after it leaves both, or on Esc, as WCAG 1.4.13 asks of content shown on hover. The dots say which names open code before the mouse finds them, as a mark on the name rather than a chip under the line: chips under calls were the version before, and on delphi-code #2 29 of 54 repeated a call shown earlier, which is why they went with the page's other elements. A mark only under the mouse was the first version of the card, and two quieter marks were drawn: the dots only on the line under the mouse, which leaves the names hidden until the mouse reaches the line, and every name lit while ⌥ is held, behind a key nobody guesses. The dots are in the text's own color, which passes on every line and word tint; muted grey was 2.85:1 on a changed word in dark. Three other forms were drawn and rejected: jumping to the definition's card, which loses the reader's place for code they mostly want a glance at; the code opened in the lines under the call, which pushes the code being read down; and a column beside the code, which costs the width the code needs. A click on the name does nothing, as a click on any code. One card serves the page: Base UI's preview card takes a handle, and each call is a trigger carrying its parts. Calls into code the PR doesn't change aren't marked; that needs the checkout, read when a name is pointed at.
- **The tour,** the third layout, in the bar's switch with a route for its icon once a run has written a tour while the Display menu's Tour (preview) switch is on, kept per browser and on by default. It's a strip of where the steps are: a box for each directory the steps' lines are in, once, by the overview's own grouping and labels, in the order the steps first reach them, and no arrows, since the steps go by what matters and not along a path; a box has its steps' numbers, a step with lines in two directories in both, and the current step's, the last whose top has passed the compact strip, a heavier border, a filled number and Current step. A box names its directory on one line and its parents above it, cut from their middle to 30 characters as the tree cuts a path, so the directory beside the name stays, and the full path is its tooltip. The directories no step reaches were a row of dashed chips under the boxes, Not on the tour, and a button on the compact strip counting them; they went as noise, since the ledger already lists every file the tour didn't show. The strip's labels are in a mono face, so a count of characters is what fits. Ending the parents with an ellipsis was the version before: on graal #15134 two boxes read `substratevm/src/com.oracle.svm.hoste…` over `pgo`, the steps' numbers were pushed out of their boxes, and the ten directories off the tour, a box each in a column, made the strip 825 px tall. A box for each run of steps in one directory was the version before, while the tour ran in call order, with an arrow between boxes and a dashed group around the two boxes of a step in two directories: the numbers only rose along it, and a directory the tour came back to was there again. That had replaced one box per directory joined by arrows, where on graal #15134 the boxes read 1 2 4, then 3, then 5 7, then 6, and the arrows said the tour ran straight through four directories when it came back to two of them. Without a path there's no arrow to say it. The strip is part of the page and scrolls away with it. Once it has, a compact strip takes its place under the bar: the strip on one line, each directory by as few of its last directories as tell it from the others on the tour, without the package every Java module among them starts with (`hosted/pgo` and `core/pgo`, not `com.oracle.svm.hosted/pgo`, which put six boxes on two rows). It's drawn over the page from a sticky element of no height, so it takes no room, and it's for the pointer alone, hidden from the accessibility tree and the Tab order, since the full strip already says it; below 1180px it's the only strip, part of the page, and a keyboard's too. One strip that was sticky and shrank once stuck was the version before: shrinking moved everything under it up by the difference, 36 px on the fixture and 780 on graal #15134, where the first scroll threw the reader from the top of the tour into a step's code, past its sentence. The window scrolls, since the bar, the cards' headers and `scroll-padding-top` rest on it. A click on a box goes to its lowest step. Each step is its number, its sentence, chips of the analysis's points on its lines, and a card per excerpt: its file, its lines, Open in code, and its rows from its first line to its last, both sides, drawn by the part's own card, with the comment box and the drafts, so a comment written there is in the map and in Publish. Its header said how many of the file's changed lines it shows, "8 of 164 changed lines", in the version before: the ledger after the steps already counts each file's lines no step shows. After the steps, what the tour didn't show: a group each for the rest of the steps' files, tests, generated and proved mechanical files, and the others, every file with the changed lines no step shows; and the findings on no step, each headed at the steps' level, and nothing when both are empty. The suggested depth after them, the steps with an open finding to read in the code, under a heading, After the tour, was the version before: it mostly said “No step has an open finding.”, and the steps' chips already say which have findings. `tourOf` in `web/src/pages/review/tour.ts` is the pure function from the analysis, the overview and the points to all of it, and its tests hold the ledger's lines and the steps' to the PR's. Open in code shows the map on the excerpt's lines, marked on their numbers with the primary and a rail, as a finding's are in its severity's color, where no point marks them, under a label naming the step. The switch and Esc there return to the step, and the switch from the map otherwise goes to the step last current, kept per analysis in `sessionStorage`, and from the tour to the current step's lines. A chip opens its point's card in the map.
- **Overview:** the changed directories as a layered diagram. A box is a directory: its path, its file count and its entries (routes, a page, a command), colored as mechanical when every change in it is. Its path is the tree's, without a Java module's repeat of its name, and one too long for the widest box loses whole directories from its middle, `src/test/java/…/orders/controllers/payments/`, as a tree heading does, the full path in its tooltip; a file's name loses words from its middle, never its extension. Cutting at the end was the version before: on a GraalVM PR every box began `substratevm/src/com.oracle.svm.core/src/com/o…` or `compiler/src/jdk.graal.compiler/src/jdk/graal…`, and the directories that told them apart were cut off. Geist Mono is 7.2 px a character at the label's size, where 8.6 was assumed. Directories nothing in the PR calls are on top, each one row below its lowest caller. Edges are the imports, calls, type uses and requests between the directories' files, merged into one per pair of boxes; one carrying a request is drawn apart, because it crosses into another process. Two directories that call each other keep the edge joining more pairs of files pointing down, and the other runs up the side; on a tie, or in a longer cycle, the edges into the directory a flow reads first run up, as for files. Tests and test helpers are badges on the directories they reach, and generated files are faded. A directory no edge touches and a test that reaches no changed code aren't drawn: the tree lists every file, and the overview is for how the changed code connects. Under the diagram were a strip of the directories, Not linked, and a list of the tests, Tests that call no changed code, before that; and before them each test was a box in its directory, which in Java, where tests are in another source root and rarely link to the code, made a box of each test directory: on graal #15134 four of the strip's seven. A legend above the diagram said what the boxes and lines mean, and a line under it named the hovered box's files, flows and edges; both went as text nobody read, and a box's name says the same to a screen reader. The directory of the file last in view in the code is outlined. A click on a box opens its first file in the map, and the switch and Esc there come back to it; a button on it opens it in place to its files, laid out by the same rules. A box says in how many places code outside the PR uses what its files change, “used in 4 places outside the PR”, tests aside; the uses themselves are on the code, under the map's “Used unchanged in”. Faded nodes for the files outside the PR, one row below the code they use with a dashed edge up into it, grouped by directory above 10, were the version before: on graal #15134 they were 11 of the diagram's 20 boxes and 17 of its 31 edges, and what they name is read where the code is. Rows by depth, ordered by their neighbors' positions, are enough at that size without a layout library.

  A node per file was the version before, with directories only above 40 files. On delphi-code #2 its 21 files made 13 nodes over seven rows and 4 in the strip, and the two `hosting_services.py` were told apart only by their labels; by directory it's 9 boxes in the diagram and 3 in the strip, and the PR reads as the setup page, the routes, the services, the infrastructure and the domain.

**The overview as the data flow.** With the Overview's form on Data flow and a flow on the analysis, the Overview is `DataFlow`: a byline naming the model that wrote it, then one list, the source, a card per station and the end, then what the flow leaves out. `dataFlowOf` in `web/src/pages/review/data-flow.ts` is the pure function from the analysis to all of it, importing only domain code. A station's card has its name, "keeps data" with a double border when it does, when it runs, its changed lines, and its files as chips in the flow forms' two styles, a new file and existing code, the second dashed too; three or more files of one directory whose names end with the same words are one chip, by the longest such ending, that opens to them in place. Under the chips, each existing file that calls into the flow's other files says what it calls, or what's called in it, from the definition calls, the first three names. Under a card is what the station hands on, with the files that only define it; where `validateDataFlow` finds nothing joining it to the next station the line beside it is dashed and says "Not checked: no call was found between these two in the code." A file opens in the map, and Esc there comes back to its chip, or to the chip that holds it. What the flow leaves out is one line, the changed lines outside it of the pull request's, and a button per kind, other changed code, tests, docs, generated and mechanical, other files, each opening to its files; a test holds that the flow's files and those are every changed file, each once. Without a flow `noDataFlowOf` says why in one line, read from the live analysis, no review yet, a review that wasn't asked for one, one being written, or the pass's error, and the directories are drawn under it. A review that found no flow says nothing: the directories are what's left, and a line saying so was the version before. The dev fixtures and the fake server's receipts-tour have a flow; the design-system page has no example of it and e2e no spec yet.

**The overview's preview forms.** The Display menu's Overview (preview) choice, kept per browser as `overview-form`, draws the overview as its data flow, the default, as its directories, or as one of three forms of the PR's flow paths ([DESIGN.md](../../DESIGN.md) says why three). `flowPaths` in `web/src/pages/review/flow-paths.ts` is the pure function from the analysis to all three, importing only domain code as `fileOverview` does. A path starts at the entries of one of the code's flows, or else at the definitions of a file that no changed code calls, and runs what their definition calls reach (see [Deterministic prep](pipeline.md#2-deterministic-prep-no-model)): a file is a stop only where a definition the path runs is in it, so shared code is a stop on each path that runs it. Type uses aren't followed, and a request ends a path in the route it names without being followed, since the route has a path of its own. A path that starts at no entry isn't drawn when another runs every file on it: on graal #15134, 27 files have a definition that no changed code calls and that calls another, an override or a callback most of them, and 9 such paths are left. Starting at what each flow reads, its whole parts, was the version before. With definition calls it would have left out the PR's main path: `PGOInstrumentationFeature`'s `afterRegistration`, where GraalVM reaches the change, is in a class that isn't a flow's start, because other code reads one of its options. An analysis stored before the definition calls has its paths from the hints between parts. A file outside the PR starts no path: a stop that code outside uses says in how many places, with a glyph and a count, as a directory's box does. Each such file starting a path was the version before: on graal #15134, 13 of 19 rows, two of them the PR's own rows again but for a file or two. A path is a tree from the files it starts in: each stop is under the one of its callers fewest calls from the start, and names them all in its tooltip and its accessible name. `FlowPath.calls` holds the path's calls between files, every one a definition call, and no form draws a link that isn't one of them, which a test holds. A stop's order on a chain was the version before, the order a depth-first walk first reached the files in, with everything the flow lists after it: on graal #15134 34 of the rows' 99 arrows joined two files with no call between them, and `ProfileDumper` ended a row where nothing calls it. A file a flow only lists, by a type it names, is on no path. Paths that start in the same files, run the same ones and send the same requests are one path with each label: on delphi-code #2 its three routes. A stop is a file, new when the PR adds it; a file is code when it has a hunk no proof covers, isn't a test, a doc or generated, and is in a language megareviewer parses. The rest are listed by kind, and code no path runs is listed as on no path; a test holds that every changed file is on a path or in one of those lists. The lanes' columns are the stops' directories, each after the longest chain of calls between directories that reaches it, a call that closes a cycle not counting. Ordering them by where each path first reached them was the first version: on graal #15134 it put `Expander.java` right of the code it calls. `bowTie` in `flow-bow-tie.ts` puts a path on the left, standing for the files it starts in, the files that call another changed file or send a request in the middle by directory, and the rest on the right. Its links are the path's calls, one between two boxes of the middle going round their right side. A path linked to every box of its middle was the version before, whether or not its start calls it. A call back into the start isn't drawn, since nothing points left. A box of several files opens in place, by a button on it as the overview's directories do, to a box per file with that file's own links, and Collapse above the diagram closes it; the focus goes to the first of the files, or back to the box. A click on the closed box opened its first file and nothing reached the others, 24 of graal #15134's 29 files in boxes of several, which was the first version. The files as chips inside the box was the alternative: one control fewer, but the links would still be the directory's, so which of 13 files calls what stays unsaid, and a box that tall is no longer a bow tie. The page keeps what's opened, the lanes' unfolded cells too, so coming back from a file finds it there, and a closed box or a folded cell takes the focus for the files it holds. `FlowLanes` is a table, with the paths as row headers and the directories as column headers, and a cell with more than three files folds the rest behind a button, and the column of paths stays in view as the lanes scroll, except under 640px, where it would cover most of them. It draws no lines: one through a row's cells, which was the version before, joins every file in a cell to every file in the next, and the table has no place for a line from one chip to another. The stop with the pointer or the focus marks, on its row, the stops that call it and that it calls. `FlowBowTie` is buttons over an inline SVG, as the overview is. `FlowRows` is a list of trees: a stop that calls one other goes on along its line with a chevron for the call, and one that calls several has them under it, those that call nothing more on one line with no mark between them. A stop opens its first part in the map and Esc there comes back to it, as from a box of the overview. The stops are buttons in the Tab order, with no arrow keys: a preview isn't worth a keymap. With a tour, the tour's strip still groups by the overview's directories.

The overview replaced a call tree: the changed hunks as a tree of symbols from the entry points. On delphi-code #2 it had 42 rows for 29 hunks, 13 of them "above" references to a hunk placed higher, three test files among its seven roots, and 19 hunks under "Not on a call path". Its rows were symbols, so it never showed that the PR runs from the routes through the services to the host classes and the keychain. Reviewers didn't use it. A tree of the code's flows instead of symbols is the alternative kept for later.
