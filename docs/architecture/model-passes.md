# Model passes

Only when the reviewer asks, on the **model option** they choose: a model on a provider, which is what runs the passes and decides who pays. The same model on two providers is two options, since the bill differs. A provider answers its own status and its options, and the list is their answers together: Haiku 5.5, Sonnet 5.5 and Opus 5.5 on Claude Code, then the same three on the Anthropic API, then GPT-6 Luna, GPT-6 Sol, GPT-6.1 Sol and GPT-6 Astra on Codex, those of them the reviewer's `codex debug models` lists, then every chat model the reviewer's opencode offers, grouped by the provider behind it. One list of models, with the provider picked for them, was the alternative; it hides who pays, which is what a reviewer chooses by. A model is listed once the evals have run on it, with its scores in a report under `evals/reports/`, because the prompts were tuned on Haiku and a wrong finding costs the reviewer more than a missed one; listing every model a provider serves was the alternative. opencode's are the exception: they're whatever the reviewer connected, and the evals can't run on all of them, so every one is listed; listing only models measured elsewhere would leave out local models, the reason to use opencode. GPT-6.1 Sol and GPT-6 Astra on Codex are the others: they were added before the evals ran on them. The analysis records the option its run used, and the page names it (see [Review page](ui-review-page.md)); Remove AI review and a new run is how another model is tried on the same PR. One option runs every pass, with the same prompts: a model per pass, or prompts per model, would each be a model the evals haven't measured.

The default, when the reviewer hasn't chosen, is **Sonnet 5.5** (`claude-sonnet-5-5`) on the first provider that can run it. On the 14 eval cases through Claude Code it met 9 of the 12 targets against Haiku's 7: no wrong findings where Haiku had 21% (6 of 28), 7% of its decisions noise against 36%, and every contract hunk marked where Haiku missed 4 of 25 (`evals/reports/2026-11-14/`). It was faster too, about 3.5 minutes for the run against 6, because it writes a quarter of Haiku's output tokens. Those evals had the risk and decisions passes, which are gone since. It costs about 4× Haiku at API prices, $0.17 a case against $0.04, and on a plan more of its usage limits. Haiku stays the default was the alternative; the cost is still cents a PR, and the menu offers Haiku to a reviewer who wants it. Opus 5.5 met 8 targets at more than twice Sonnet's cost.

Each Claude model's ID, name, price, input budget, output limit under each transport and the efforts it accepts are in one table in the adapter, `src/adapters/model/claude/models.ts`, and each OpenAI model's slug, name and price in `src/adapters/model/codex/models.ts`, its context window and efforts coming from Codex's catalog; a pass whose effort a model doesn't accept runs at the nearest one it does. The prompts, input rendering, output schema and pass model every provider shares are in `src/adapters/model/shared/`, apart from Claude's transports, so a provider imports only those, never another provider; the dependency rules check it.

Every pass answers with JSON checked by the same Zod schema, through one of four transports that share the prompts and the input rendering. Claude Code and Codex enforce the schema as structured output; the API and opencode are asked for it in the prompt:

- **Claude Code,** the default: one `claude -p` process per pass, on the reviewer's own Claude plan, so a review isn't billed per token on top of a plan they already pay for. The Messages API can't spend a plan; Claude Code can. Each runs without a shell in a new empty directory, with no tools but the schema's `StructuredOutput` and, on a run with something to read, the reader of [Reading the harness](harness.md#reading-the-harness), no MCP servers, settings, skills, commands or saved session, and the answer comes back as the stream's `structured_output`. No MCP servers is `--strict-mcp-config`, except where an organization deployed a `managed-mcp.json`: Claude Code then refuses that flag and loads the file's servers whatever else is asked, so megareviewer reads the file's server names and denies each one, and every remote server by URL, with `--settings`. The session's first event must still list no servers. Retrying without the flag after the error was the alternative; it costs a process per pass and still needs the names to deny. Claude Code has no token count, so the size check estimates tokens from the prompt's bytes, high on purpose: 1.9 bytes a token and 2,000 tokens for its own, where the eval cases measured 2.06 and about 1,550.
- **The Anthropic API,** the fallback: one streaming request per pass with the SDK, with no output format. The API compiles a format into a grammar and refuses one too large, and the passes' union is: 400 "The compiled grammar is too large, which would cause performance issues" on Haiku 5.5 and Sonnet 5.5, for a schema under every limit the API documents. On a run with something to read it's a request for each round of [reading](harness.md#reading-the-harness) and one for the answer. So each pass's task ends with the JSON schema of its own answer, its variant of the union, in the words opencode's does, and the answer's text is read the same way, a code fence or a sentence around it tolerated, then checked by the same Zod schema; the pipeline retries an invalid one once. On small-feature and prompt-injection on Sonnet 5.5 all five passes, the tour's steps pass among them, answered valid JSON first time, and the four after the intent read the PR from cache, 4,116 tokens each on small-feature. The union was the format before. Sent to today's API as it was at each commit, it was first refused when findings gained their lines, suggestion and mismatch (2026-11-13), fit again once the tour pass was dropped, and has been refused since the intent's brief added `shape` and `watch` (2026-11-16): 3,690 bytes of schema, where the 3,597 before them are accepted. A risk's checking test and the guidance mark each added to a schema already refused; the union has lost the risk and decisions variants since, and wasn't tried as a format again. Nothing caught it: counting tokens doesn't compile the grammar, so `checkSize` passed, the adapter's tests replay answers, and the evals ran through Claude Code, which takes the schema as a tool and accepts it. `evals/claude-live-check.ts` is the check that the API takes the requests, and runs every pass. A format per pass was the first alternative, since each variant alone is accepted: the format is part of the cached prefix, so the second pass wrote the PR to the cache again, 5,235 tokens written and none read, and unlike effort `format` can't be set in a message after the PR. A looser union for the API to enforce, with Zod checking the rest, was the second: the grammar's size follows the whole schema and not one costly part, so the union without any enum, without any nullable, with shared `$ref` definitions, or as one flat object is still refused, and the API takes no schema that leaves a value open (`{}`, an array without `items`, an object without `additionalProperties: false`). Cutting fields until it fits would hold until the next field is added.
- **Codex,** for OpenAI's models: one `codex exec` per pass, on the reviewer's ChatGPT plan. Each runs without a shell in a new empty directory, with our instructions in place of Codex's (`model_instructions_file`, which also saves about 4,300 tokens a call), the answer's schema as `--output-schema`, the read-only sandbox, `--ephemeral` so the review isn't in the reviewer's Codex history, and none of their config, rules or `AGENTS.md`. The answer is the last message's text, parsed as JSON and then with the same Zod schema. Its size check estimates 3 bytes a token after 6,000 of Codex's own, where the eval cases measured 3.36 to 5.19 bytes and about 5,300 tokens, against the model's context window less 32,000 for the answer. Codex reports tokens and no cost, so the cost is computed at OpenAI's API prices, or absent for a model without one.
- **opencode,** for the models of the reviewer's own providers: a session per pass on the one server, run as an agent megareviewer defines in the server's config, whose system prompt is the shared one, with the [reader](harness.md#reading-the-harness)'s directory and permissions on a run with something to read. opencode 2.3.0 has no structured output a prompt can ask for, so the pass's task ends with the JSON schema of its own answer, its variant of the union, and asks for one JSON object and nothing else; the answer's text is parsed, a code fence or a sentence around it tolerated, and checked by the same Zod schema, and the pipeline retries an invalid one once as for any transport. Provider-native structured output through a provider's request body was the alternative: each provider package names the field differently, the config is fixed for the server's life, so one schema for every pass, and Anthropic refuses the union as too large a grammar. On delphi-code #2 through Haiku 5.5 every pass answered valid JSON first time. The session is deleted once the pass is read, since opencode keeps it in the reviewer's own history, and it's given a title, so opencode doesn't spend a call naming it. The size check estimates 1.9 bytes a token, Claude's rate, after 2,000 of opencode's own, against the model's context size from the server's list less 32,000 for the answer. The cost is what opencode reports from its model catalog, absent for a model the catalog has no price for.

On Claude's two transports, the passes share one cached prefix holding the PR context, so a pass that starts after it's written reads the PR from cache. Effort is set per pass. Changing the output format between requests would invalidate that cache, so through Claude Code every pass of a run sends the same output schema (a union of the passes' outputs, tagged by pass), and on the API none. Where the PR data sits differs:

- **On the API,** it's a user message, after the system prompt, and each pass sets its effort in a system message after it, since a different top-level effort would invalidate the cache.
- **On Claude Code,** it's in the system prompt, after the instructions, which end by saying what follows is data. That's the only placement Claude Code caches across processes: measured with 30.5k tokens of PR data, the second process read 29,887 tokens from cache with the data in the system prompt, and none with it in the user message, as one text or as a block of its own. Effort is the `--effort` flag, which doesn't miss the cache; another schema does, since it's a tool before the system prompt. On delphi-code #2 the later passes read the PR from cache, as the stage 41 doc records. Forking one saved session per pass was the alternative: it keeps the data in a user message, and writes the PR's code into `~/.claude/projects` as sessions the reviewer then sees in Claude Code.
- **On opencode,** it's in session instruction entries, which opencode puts in the system prompt before its last cache breakpoint; the task is the prompt. On delphi-code #2 through Haiku 5.5 each later pass read 127,219 tokens from cache. A synthetic message before the task read nothing from cache, and the PR in the task's own message can't be shared. An entry can hold 262,144 bytes as opencode counts them, JSON-encoded, so a larger PR is cut between lines into entries keyed in the order opencode joins them; delphi-code #2 with its unchanged callers is 363 KB. The route is experimental, which the version check guards.
- **On Codex,** it's in the instructions file, after the instructions, as on Claude Code, and the pass's task is on stdin. OpenAI looks a cache up at message ends, so that's the only placement a later pass can read: on stdin the PR and the task are one message. But the cache rarely holds across processes: Codex sends a new thread's ID as the cache key on every `codex exec`, and a cache lives on one machine, so on delphi-code #2 one later call in 11 read the PR from cache. A run pays for the PR in every pass, about 32k input tokens of the plan's limits each there. Resuming one thread for every pass was the way to share the key, and was left: it carries each answer into the next pass and writes the session to the reviewer's Codex history.

The findings read the intent's answer, to name the mismatch a finding shows, and the steps pass reads no other's. The intent pass starts first and writes the PR to the prompt cache, and the findings start when it ends. The steps pass starts as soon as the intent's answer begins, when the PR is in the cache, and reads it from there; Claude Code says so with the model's first message, the API with the stream's first event, and Codex and opencode say nothing until the answer is done, so there it waits for the intent to end. On Claude Code the model's first message comes as its thinking ends, a moment before the answer, so both start about when the intent ends. A risk and a decisions pass ran beside the steps until the risk and decision points went (see DESIGN.md). Every pass starting at once was tried: each wrote the whole PR to the cache, and on the evals the passes cost 2.5 times as much at API prices, $2.27 against $0.78 on delphi-code #2.

| Pass | Output | Effort |
|---|---|---|
| Intent | Stated intent (description, tickets), intent inferred from the code, and mismatches between them | medium |
| Findings | What looks wrong, as a draft comment: a title of at most 80 characters, an explanation of at most 300, the hunk and lines it rests on, a type (logic, contract or architecture), a severity, a suggested change for those lines or none, and the intent mismatch it shows or none | high |
| Steps | Only for a run that asks for the tour: 3 to 7 steps, what matters most first, each a sentence of at most 20 words of something the change makes true and the lines that show it, in one place or two | medium |

Intent is kept short, because the reviewer reads it before any code: each summary is one sentence, with at most 5 behavior changes. The inferred intent's summary is the header's brief, at most 20 words that don't repeat the title. What the code does that nobody asked for, or does differently, is a mismatch even when the summary leaves it out, and the prompt says so; what changes for existing code or data isn't, which naming it beside them made one on the evals, two more false mismatches on the baseline's 24 cases. It said it of the brief's watch line while the pass wrote one, a shape and at most 2 things to watch beside the summary: without it, on the evals' large-retry-after the brief said the unrequested body-read timeouts and the pass reported no mismatch, in two runs of two, so nothing marked the code. The page stopped showing the two, and the pass stopped writing them; an analysis stored with them parses without them. The findings pass reads the intent's summary and mismatches. The findings pass is the model's job: triage. It looks for three types of finding, each with a bar, an example that counts and one that doesn't: a contract finding names what breaks outside the PR and shows it, and an architecture finding names the code in the data it goes against, one of three things (see DESIGN.md). A finding is one type, contract when it's also another. It lists at most 10, most important first, and only what the code in the data shows, because a wrong finding costs the reviewer more than a missed one. The server checks that each one's hunk exists and that the hunk shows its lines; one still wrong after the retry is dropped and logged. A finding posts as the reviewer's comment, so the prompt asks for plain words: what happens rather than the class of problem it belongs to, a technical term only where it's the exact name, short sentences, and the code's own names and values kept, since plain isn't vague. Told only to write to the author in 300 characters, Sonnet wrote "`beforeThreadRun` callocs `ALLOCATION_BYTES`", "a privilege escalation" and "a privacy and compliance decision", which the author has to translate and the reviewer to reword before posting. On the evals it found what it did before, with fewer long words and asides (`evals/reports/2026-11-25/`). A second model call that rewrites the findings was the alternative: seconds on every run, and a rewrite can change what a finding says after the server checked it. A setting for the tone was the other, a choice nobody needs to make. A risk's reason and a decision had the same words asked of them while they were points, after their tasks and never changing what was decided. A title or explanation longer than the prompt asks is kept as written, with no retry: on delphi-code #2 one explanation over 300 characters cost a second findings pass, 2 of the run's 5 minutes, and one still too long after the retry was dropped, a real finding lost for its length. A suggestion on base-side lines, which a comment can't replace, or a mismatch the intent doesn't have costs the finding only that, after the retry. The findings pass reads the intent's mismatches by ID, so one finding carries a mismatch it shows instead of the reviewer reading it twice. Matching them on the server by the hunk they rest on, so findings could start beside the intent, was tried: a hunk often holds two mismatches, and on the evals it gave description-contradicts' constant delay the mismatch about retrying 4xx errors.

The passes read the **unchanged callers** the analysis has, as an `<unchanged_callers>` block at the end of the PR data, in the text every pass shares and in the size check: each changed definition by name and the hunk that changes it, then each use with its file, line and the excerpt megareviewer keeps, escaped as PR content is, since it's code from the same repository. With none, nothing is written, and the text is byte for byte what it was, which a test holds. A run reads them from the analysis it starts from and never from a checkout, so a run that starts while the repository is downloading reads the PR without them. When the hunks fit only without the callers, the callers are left out after the files' contents, and a warning says so: a PR that could be read before they were isn't refused because of them. On the 24 eval cases, six of them made for the types, the first prompt tried found every contract and architecture must-have, with the label's type on 21 of 21 findings, none of 27 rated noise, and nothing on the two cases where an API or a credential is touched and nothing breaks (`evals/reports/2026-11-25/finding-types.md`). It's one run, and architecture is two small cases.

The model's results reach the page as **points**: the findings by severity, blocking first, then the intent's mismatches no finding names, which is why the header has no mismatch chip, each in the model's own order. A finding's ID is still its place in the model's answer. A finding stored before there were types is logic, which is what the pass looked for. `pointsOf` builds them in the domain as a pure function of the analysis. An analysis stored with risks and decisions parses without them and shows its findings and its brief: the stages of the two passes are left out, an error of one of them is dropped unless the intent or the findings didn't finish, and their usage and calls stay, so Run details lists what ran. A stored state or review signal of a risk or a decision still parses, since the suggestion call reads signals.

The model doesn't title the flows. A tour pass did, last, since it read the other passes' answers: a title of at most 80 characters naming behavior ("Save a host's token", not `PUT /api/account-connections/{domain}/token`) and an explanation per step, and merges of supporting steps into the steps they belong with. It added 8 seconds to the end of every run for titles only the overview shows, so it went while the run is brought toward 20 seconds; the overview labels flows by the code's titles. Before it, the model wrote its own tour, at most 7 steps, which on delphi-code #2 grouped by layer, with the three routes in one step: flows the reader can check against the call graph are worth more than the model's grouping. An analysis the tour pass titled loads with the code's titles, which it kept beside the model's. A flow is now its title, its parts, its kind and its entries: the tour pass's explanation, its merged steps and `builtBy`, each step's ID, and `via`, the earlier code a flow passed through, went once nothing read them, with the check that every part was in one step, which only the tour pass needed; an analysis stored with them loads without them. The overview reads the flows from the analysis and keeps a part no flow lists in its place, after the flows' parts in path order.

The **steps pass** writes the page's tour, which the Tour layout draws (see [Layouts](ui-layouts.md)), and runs only when the run asks for it (`RunModelRequest.tour`, which the page sends while its Tour switch is on, or its Overview switch is on and the Overview's form is the data flow). It reads only the PR, from the prompt cache, and starts once the intent has written it there. Through Claude Code and Codex, a run that asks sends every pass the union with the steps pass's variant, so the three share one cache; a run that doesn't sends the union of the two, which the fingerprint tests hold for each, beside a fingerprint of their own for a run with the tour. The API and opencode send no format, so there the two passes' requests are the same with the tour or without, and the steps pass's task ends with the schema of its own answer as theirs do, with a fingerprint of its own. Sending the union with the steps variant always was the alternative: one schema, but a run without the tour would have paid for a schema it never answers, and its requests would have changed. The server checks the steps with `validateSteps`: each excerpt on a hunk sent in full and on lines it shows on its side, a step's two excerpts on no line of each other's, at most 7. The order is the model's, by what matters most to understanding the change, and nothing checks it. While the tour ran in call order the server checked that too, no step before one whose code calls its own by the call graph's direct hints between their parts, and that a step's two excerpts were in different files; on graal #15134 a tour by meaning broke the first six times and the second once. One retry is told what's wrong; after it a bad excerpt is dropped, the second of two on the same lines is dropped, a step left with none is dropped, steps past the seventh are dropped, and fewer than 3 left is no tour, with why. The task's sentence and its excerpts' length are asked for and not checked: an excerpt is usually 4 to 14 lines and can be more, 49 for an option and its help on graal #15134. An answer of fewer than 3 steps is a change too small for a tour. The pass is optional to the run: the review's two stages decide whether the model can run again and the run's error; a steps pass that fails is its own stage's `failed` and the analysis's `stepsError`, never `modelError`. It does keep the analysis in progress while it runs, so the events stream until it ends and a server stopped mid-tour fails only the tour at its next start. Remove AI review takes the steps off with the rest of the run. The union check of stage 64 found the Anthropic API refused the union as too large a grammar with the steps variant and without, which is why the API transport sends no format (see The Anthropic API above).

The same answer holds the change's **data flow**, or none (`Analysis.dataFlow`, [DESIGN.md](../../DESIGN.md) says why the model writes it): where the data comes in, 2 to 7 stations in the order it moves, each with a name, when it runs, whether it keeps data, its changed files, what it hands the next and the changed files that only define that, and where the data ends up. `validateDataFlow` in the domain checks it against `dataFlowContext`, the pull request's paths and every pair of them a call-graph hint, a definition call, a request or an import joins: a file that isn't the pull request's or is placed twice, a station without a name or a file, stations past the seventh, and two neighbors nothing joins, counting what the first hands on. The problems go to the pass's one retry beside the steps'. After it `keptDataFlow` drops those files and stations and keeps neighbors nothing joins, which the page marks; fewer than two stations left is no flow. The flow stands by its own checks: an answer too small for a tour can have one, and a tour can have none. Its texts are mended of refs as a step's sentence is. The variant is in the union only a run that asks sends, so a run that doesn't sends what it did, and the transports' tour fingerprints moved with it; their prompt versions didn't, as when the pass was added. Claude Code took the union with the flow in one small call on Haiku 5.5 (`evals/union-check.ts`); no pass has written a flow of a real pull request yet. The union check of stage 64 found the Anthropic API refused the union as too large a grammar with the steps variant and without, which is why the API transport sends no format (see The Anthropic API above).

The server validates every response: every referenced hunk ID must exist. On failure it retries the pass once with what was wrong, then shows the error. Hunk IDs that still don't exist after the retry are dropped from the intent's mismatches, and the server logs it. The page doesn't warn about it: the first version did, but a reviewer can't act on the model's mistake.

PR content is untrusted. A description or code comment can contain text aimed at the model, so:

- The model has no tools, but for one reader of the harness's files, on Claude Code, the API and opencode (see [Reading the harness](harness.md#reading-the-harness)). On the API there's nothing else to turn off: the request names the one tool, megareviewer serves it from memory, and no path the model gives reaches a disk. With Claude Code, it's checked on every call. The stream's first event lists the session's tools and MCP servers, and anything but `StructuredOutput`, with `Read` and `Grep` on a pass that reads, and no servers kills the process and fails the pass, as does an API key in use when the startup line says the plan, so a Claude Code update that changes a flag's meaning fails loudly instead of handing PR text a shell. The worst a prompt injection can do is distort the analysis.
- Claude Code also reads files without a tool: an `@/path` in the message on stdin attaches that file to the prompt, whatever `--tools` says, and neither the path nor the content is on the stream, so the check above can't see it. The guardrail call's message holds PR code, the suggestion call's holds comments and the findings pass's holds the intent's answer, so a PR could have had a file of the reviewer's sent to the model. Through megareviewer's own guardrail call on 2.1.303, an `@` before the path of a 40 KB file took the cache-write tokens from 850 to 13,729, and before a directory's, to 6,702 for its files' names. `claudeEnv` sets `CLAUDE_CODE_DISABLE_FILE_MENTIONS`, which Claude Code has had since 2.1.299, below the oldest version megareviewer runs. Escaping every `@` in the data was the alternative; it would change decorators, scoped packages and path aliases in the code the model reads, and rest on guessing what Claude Code takes for a mention. `--restricted` alone was another; it refuses a path outside the directory and still attaches one inside it. In the system prompt file, where the PR is, an `@` isn't expanded.
- Codex's tools can't all be turned off, so its lockdown is different: no tool runs unseen. Every feature that adds one is disabled, and what's left (`exec`, `wait`, the agent tools, MCP resources) is watched on the stream, read as it arrives: any item but the model's reasoning, its message or Codex's own errors, an item type Codex doesn't have yet among them, kills the process and fails the pass with "the session used a tool", and its answer is never read. Under it, the read-only sandbox blocks the network and writes, as measured on macOS (stage 52's doc), so a command that did start could only read files and pass them to the model, whose answer is then thrown away. Code mode's `exec` runs without putting an item on the stream, so it's turned off (`code_mode_host`), and fails closed. Accepting the sandbox alone was the alternative; a command's output could then reach a finding the reviewer publishes. The bound is the same: the worst an injection can do is distort the analysis, or fail the pass.
- opencode's agent is denied every tool by its permissions, a final rule denying everything, the last match winning; that leaves the model one tool, `skill`, which can't be removed and has nothing to load. A session with something to read is given leave for `read` on its own files after that rule, and nothing else. Its answer is read only once the session is idle, and a session holding anything but the prompt, one answer of text and reasoning, the turn's end and, where it may read, its reads (a tool call, a shell, a skill loaded, a second step with nothing read, or a message of a kind opencode adds later) fails the pass with "the session used a tool", its answer discarded. A PR description asking for a shell and an SSH key, on small-feature's input, ran nothing: the model had no tool to run it with, and reported the request as a finding.
- Model output is rendered as text, never as HTML.
- Mechanical proofs come from deterministic code, not the model.
- What preferences are suggested from is untrusted the same way: a point's title was written by a model reading PR text, and a comment quotes code. The suggestion call runs under each transport's lockdown, and its output is only ever a proposal the reviewer reads and accepts.
- So is what the guardrail call reads: a point's words were written by a model reading PR text, its code is the PR's, and the configs and build files are the repository's. It runs under the same lockdown, and its answer is only ever marks the server checks and the reviewer reads: it can mark a point, never change one.

**Size limits.** Mechanical hunks are sent as path plus stats, not content. If the PR still doesn't fit in the context window, full file contents are left out, largest first, as few as fit, and nothing says so: they're context the model reads beside the hunks, and a warning about them was one the reviewer couldn't act on. "Full file contents omitted for N files" was the version before. If the hunks alone don't fit, the analysis fails with a clear message. Hunks are never truncated.

**Model and cost.** Per million tokens, Haiku 5.5 is $0.10 in and $0.50 out for prompts up to 100K tokens, five times that above; Sonnet 5.5 is $2 and $10, and Opus 5.5 $4 and $20. On the eval cases a PR cost $0.04 on Haiku, $0.17 on Sonnet and $0.40 on Opus at API prices. Each reviewer pays for their own analysis, so cost per review decides whether people run it at all; the menu shows who pays for each option, not its price, which the usage line says after the run. Through Claude Code nothing is charged per review: the passes come out of the plan's usage limits, and the usage footer shows Claude Code's cost at API prices as an estimate, "≈ $0.02 at API prices, on your Claude plan". Opus 5.5 was the first choice: stronger analysis, but on the order of $1 per medium PR. Haiku 5.5 came next, the cheapest, and Sonnet replaced it as the default once the evals measured both. A refused pass fails with the model's reason instead of being answered by another model: the API's server-side fallbacks aren't used on Sonnet or Opus, since a pass answered by a model the reviewer didn't choose would be named after the one they did. Whether a plan serves a model isn't known before the call, so a plan that refuses one fails the run with Claude Code's reason. Through Codex, GPT-6 Luna is $0.10 in and $0.50 out, GPT-6 Sol and GPT-6.1 Sol $2 and $10, GPT-6.1 Sol $4 and $15 for prompts over 272K tokens, which its 500K window allows, and GPT-6 Astra $10 and $50, from OpenAI's price list; the usage line says "on your ChatGPT plan", and for a model OpenAI doesn't price it shows tokens and says the cost is unknown, rather than borrowing Claude's: one vendor's prices say nothing about another's. Through opencode the cost is opencode's own figure from its model catalog, billed by the provider behind it: $0.24 for delphi-code #2 on Haiku 5.5. A local model has no price, so its cost is unknown rather than zero.
