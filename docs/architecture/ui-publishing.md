# Approving, publishing and comments

**Approve** in the bar posts a review with the approve verdict and nothing else, at once: no summary and no line comments, so drafts still waiting stay for the next review, since nothing is posted that the reviewer hasn't seen in the dialog. Its ID is kept until the host answers, as the dialog's is. It's sent with `allowStale`, so it goes through when the PR has new commits since the analysis, whether the page knows of them or not: nothing in it is anchored on a line. On GitHub the approval names the analyzed commit, the code the reviewer read, as any review from here does; Bitbucket's approvals name no commit. Refusing it until a new analysis was the version before: a reviewer who had looked at a small push on the host, or didn't mind it, had to run an analysis only to get the button back. The dialog still asks first, "Publish anyway?", since its review can have line comments. Approving through the dialog only was the version before: three clicks for the review a reviewer with nothing to say sends most. **Revoke approval** (`DELETE /api/analyses/:id/approval`) takes it back at once, with no dialog, as Approve gives it, and the PR's status is read again. Like publishing it's never retried; with no approval standing it does nothing, so sending it again after a lost answer is harmless. GitHub has no way to withdraw an approval but to dismiss the review that gave it, which needs write access to the repository, and on a protected branch the right to dismiss reviews; when the reviewer lacks it, GitHub's reason is shown. Submitting a review that requests changes was the alternative on GitHub, and would say something the reviewer didn't mean.

**Publish.** Sends the review to the PR's host. The comments the reviewer wrote on hunk lines, those a raised point opened among them, go on those lines; nothing is written on their behalf. The reviewer picks the verdict in the dialog — comment (the default), approve or request changes — except on their own PR, which hosts don't let the author approve: there approve and request changes are disabled, with a line saying why, rather than hidden, which left a reviewer looking for them. It followed from counts of verdicts on decisions before there were points; with points, saying nothing means fine, so there was nothing left to count. The user confirms before anything is posted, in a dialog of only what posts: the comments as they'll read, with their file and lines, the verdict, then a field for an optional summary, and a button that says it, "Publish 2 comments", with the verdict last, "Publish and approve": the verdict's own button is "Approve", and two of that name in one dialog read alike. The summary posts as written. Nothing else is added. The comments scroll in a box of their own, so the verdict, the summary and the button stay in the window however many and long they are; the whole dialog scrolled at first, and with six long comments at 1440×900 the verdict and the button were under the window's edge, where a reviewer didn't look for them. The dialog before showed the verdict and why, a warning about decisions not reviewed, a preview of the summary repeating the reviewer's text, and a summary that added "2 comments on the code." and "_Reviewed with megareviewer_". Publish is offered on any complete analysis, since an approval with nothing to say is a review in itself, but not with a comment that says nothing: GitHub refuses a comment review without a body or a line comment, and Bitbucket would post nothing, so the button waits for one and says what's missing, and the server refuses it too.

An analysis publishes as many reviews as the reviewer sends, each numbered from 1, so a reviewer who commented first can approve later. Each is a row of `publications` and its comments are recorded under its number in `published_comments`: a retry after a partial failure continues the number after the last finished review, skipping what that number posted, and the next review starts clean, so it can post on a line the first did, and GitHub sends its verdict with it rather than as a comment, as it would if the first's summary counted as posted. The dialog picks an ID for its review when it opens and sends it on every retry, and a request whose ID already published gets that receipt back: a retry whose first answer was lost doesn't post the review twice. One publication per analysis was the first version, and a second publish returned the first's receipt, so after commenting the bar said only Published and the reviewer couldn't approve from megareviewer at all. A button that sends only a verdict after a publication was the alternative; on GitHub it's a review either way, and a second review needs the line comments written since as much as the verdict. Clearing the records after a publication was rejected, since they're what makes a retry safe, and so was sending the time of the last review the page saw instead of an ID: a second tab's review would then get the first tab's receipt, and its drafts would be cleared without being posted. The review activity counts each publication, and a PR once a day however many reviews it got. The bar shows Published, linking to the latest review, beside Publish review…, and the dialog says when a review is already on the PR. The points stay read-only after the first review, which answered them, but line comments stay open: a new one goes with the next review, or posts now with Comment now. The drafts a review posted are cleared from the browser, since they're threads on the host now and are read again. Locking the line comments with the decisions was the first version; a review published early left nowhere to say what came up after. A new comment could only post now after that, until a second review could carry it. Its button ends the bar, "Publish review…" with a count of what it will post (the comments on lines), so it's in reach however far the reviewer has scrolled. It was in the header first, out of reach once the code scrolled past it, then floated at the bottom right of the window, with room left under the page's end for it. A bar that stays on top was rejected then, because it costs a row of code on every screen for one button; it holds the pager now, which has to be in reach from every point's card, so the row pays for itself and Publish moved into it. A box at the foot of the file tree was the other alternative; the tree is behind a button at 1024px or less.

Comments on hunk lines are drafts in the browser's local storage until they're sent with the publish request, which checks that each is on a line the diff shows. A `hunk_comments` table with its own routes was the plan; the drafts belong to one reviewer in one browser, and the posted-comment records already make publishing safe to retry. A line's number opens its comment box, and closes it again; the code is text, and a click on it does nothing. While the pointer is on the line its number has only a quiet plus before it, and the cell fills edge to edge once the pointer or the keyboard's focus is on the number itself; the plus is on the number rather than in the marker column, where it would read as an added line's. A finding's bug is where the plus would be, so it stays while the pointer is on the line and gives way to the plus when the cell fills, where its red would be lost. A rounded chip with the plus at its far edge was the first version, and read as apart from the line. A draft can cover a range: a drag down or up the numbers of one side in one part, marked as it goes, or ⇧-click on a second line. The drag follows the rows, so the pointer can stray from the narrow column. Selecting code is the other way: a Comment button comes at the selection's end once the pointer is up, under it, or above it when it was made upwards, and opens the box on the lines the selection covers. They're the lines of the side it ends on, in the part it ends in, where the pointer let go; a line none of whose code is selected isn't one, such as the line after a triple click, and nor is one a comment can't go on, such as an unchanged line opened from a fold. The button goes when the selection does, on Esc, and while its line is out of sight, and it keeps within what its card shows of a long line. One serves the page: `selectedLines` reads the part and the lines from the rows' `data-place`. It's a pointer's shortcut, hidden from the accessibility tree and the Tab order: the number button is the keyboard's and a screen reader's way to the same, with ⇧↵ on a second number for a range. A range over the open box's lines takes its draft along, and a line that has a draft already opens that draft, on its own lines; any other draft stays where it is. Only the number opened the box at first, a small target, and a click anywhere on the line replaced it, with the line tinted under the mouse and its number filled: the highlight and a hand cursor followed the mouse over every line of code, and stray clicks opened boxes. Rejected in its place: the number alone again, the target that was too small; a double-click on the line, which selects a word; a context menu, which nobody finds and which takes the browser's; and a modifier held to click anywhere, a key nobody guesses. The box had a severity picker and a Suggest a change toggle, with a field for the suggested lines and a diff of them under the comment's own field, and has neither now: the toggle stacked three boxes in one draft. A suggestion is still a ` ```suggestion ` block typed in the comment, previewed when the draft is saved, and a draft saved before with a suggestion keeps it, shows it and posts it in its body. A draft has two states. Editing, its text is saved as it's typed, so a reload loses nothing; Add to review (⌘↵) or a click on its line's number closes it, and Cancel (Esc) puts back the draft as it was when the box opened, which for a new one is none, and for one a point's Comment or Edit opened is the draft and the point as they were before it. The box starts where the code does, past the line numbers, and the lines it's on have a bar at their edge while it's open. Its header names the file and lines, `orders.ts` and `R14–15` (L for the base's side); Write and Preview tabs show the text or the comment as it will read; and the keys are a line of words under it, "⌘↵ add to review · Esc cancel", rather than hints on its buttons. Add comment was the button's name before; it didn't say the comment waits for the review. A Discard button beside Cancel, with Cancel keeping what was typed, was the version before; two ways out that did nearly the same thing. Saved, it reads as the comment it will be, with a chip saying it posts with the review, its body and its suggestion as a diff, and Edit and Discard. Closing an empty draft removes it. The box stays open when the focus leaves it, so the reviewer can select code while writing. A box that closed when the focus left it, with one editing state, was the first version; selecting code to quote closed it, and a click on its line with the box open closed it as the focus left, then opened it again. GitHub anchors a range with `start_line`; Bitbucket can't, so its comment goes on the last line and names the range, and the comment box says so.

Replies and resolving post at once: a reply answers someone now. A new comment belongs to the review being written and goes with its verdict, unless the reviewer posts it with Comment now, beside Add to review in the comment box: it goes to the PR at once as a thread of its own, the draft goes, and the thread shows on the line when the threads are read again. Like publishing, it goes on the analysis's head or nowhere, since its lines are anchored on it: when the PR has new commits since, it's refused and the text stays in the box. Only with the analysis complete, as publishing. GitHub and Bitbucket work the same way. Without it, the way to say something now was a review of one comment, which posts a summary too.
