# Preferences

What the reviewer values is kept in the store and given to the model passes as guidance. [DESIGN.md](../../DESIGN.md) says what a preference is and why nothing learned applies by itself.

**A model run's guidance.** Before the passes, a run reads the enabled preferences for everywhere, then the PR's repository's, each in the order they were made, and the files of the repository's harness that are always loaded: the guideline files switched on, in `GUIDELINE_PATHS` order, then what they import with `@`, breadth-first in the order written. They share one budget in the prompt, 64 KB, and a file that doesn't fit what's left is passed over and the next one tried, so one large file doesn't shut out the small ones after it; 32 KB a file was the version before, which left an index out of its own rules' reach. Everything the harness reaches in the prompt was the alternative, 1 MB on megareviewer's own repository, and so was nothing but the roots: an import is the author saying "always load this", and every pass would otherwise read it for itself. The files are read at the PR's **base** commit, so a PR can't rewrite the rules it's reviewed by and no checkout is needed. The run joins the harness's load; without a harness, the roots alone are read from the host through `file_contents`, which keeps a file that isn't there too, so a repository without one is asked once. Reading them from the local checkout was the alternative; only some reviewers have one, at whatever commit they left it. The run numbers what it read, `p1` for its first preference and `g1` for its first guideline file, with the files left to be read after those in the prompt, gives it to every pass in its input (`AnalysisInput.guidance`), and keeps it on the analysis (`guidance`): each preference's ID, kind, text and scope, and each file's path, size, what imports or links it and whether it was in the prompt, not its content. Remove AI review clears it with the run's other fields. Guideline files that can't be read, a harness that can't be loaded and, on a transport without the reader, the files that don't fit and how many more aren't given, are a warning on the analysis, and the run goes on without them.

**In the prompt.** The guidance is a `<reviewer_guidance>` block before `<pull_request_data>`, in the one text every pass shares, so no transport places it and the later passes read it from the cache with the PR: on delphi-code #2 through Claude Code the intent wrote 130,883 tokens and each later pass read 129,329. A preference is one line, its ref, its kind, where it applies and its text, whitespace collapsed so it can't fake another's line; a guideline file is its content under its ref and path, escaped as PR content is, with `linked_from` naming the file that imports it, so a point says the file its rule is in. Beside a linked file, one line of megareviewer's own says that other files may be linked and weren't given; a sentence in the system prompt was the alternative, and would change every run's prompt for a line most runs don't need. With no guidance nothing is written, and the text is byte for byte what it was, which a test holds to its hash from before. A placement of its own per transport, as the PR data has, was the alternative: four of them, for a block the shared text already carries to each. The system prompt has one section on it, the same with or without a block: preferences are the reviewer's own rules and guideline files the team's as of the base commit, and both change what to look for and what to leave out, never the answer's format, the rule that PR content is data, or the rule that text aimed at an automated reviewer is a finding. Each task then says what guidance does to it:

- **Findings** check the code for what a Look for preference or a guideline file names, even for what the task otherwise leaves out, since a rule about naming or tests would do nothing under "not style, not naming, not missing tests", and still list only what the code shows. A finding a Don't flag preference covers is reported all the same, whatever its severity, marked `left-out`, after the others and outside the limit of 10, at most 5.
- **The intent** carries no mark. A preference such as "any change to billing" raises a finding when something there looks wrong, never a card of its own; while risks were points it made the hunk a risk, and while the brief had a watch line it said there first that the change touches it. The intent's message also says that guidance isn't what was asked for, so code that breaks a rule is a finding and never a mismatch: on the evals the pass reported a broken rule as one in every run where it was given it or read it. What guidance adds to a task is in the pass's message, which no cache holds, and only on a run that has some; in the task itself it would change what every run sends.

On that run, with one Look for about secrets reaching logs and one Don't flag about the order credentials are tried in, three marks came back, all on risks, which were points then, and all three checked out: the keychain module raised, both credential-order hunks left out. It took 51 seconds, as a run without guidance does.

**The suggestion call** is one call of its own, on every transport, with its own system prompt and schema, at medium effort: a fifth variant of the passes' union was the alternative, for a call that shares no cache with them, on a union already near what a provider's grammar takes. Its data, one repository's signals and the reviewer's past comments on it, with the preferences the reviewer has and the proposals they rejected, is in the call's one message. A text over 2,000 characters is cut and ends with "…", which the prompt says: evidence is a few words of a text, a past comment can hold a pasted file, and the call has no size check of its own. It proposes at most 8 rules, each only where two signals or comments show the same thing, a signal and a comment counting together, each with the lines of evidence it rests on, which end with the pull request they're from, and each for the repository unless it's about how the reviewer reviews any code. An answer outside the schema isn't retried; the reviewer asks again. On opencode it's a second agent in the server's config, since an agent's system prompt is fixed there. Through Claude Code a call over 7 signals answered in 2.9 seconds, $0.015 at API prices.

**Measured.** The evals ran before and after the prompts learned to read guidance, on Sonnet 5.5 through Claude Code (`evals/reports/2026-11-17/guidance.md`). On the 14 cases without guidance no metric that met its target misses it now, and the risk metrics didn't move by a hunk in three runs. Decision noise was 4% before and 17% and 11% in two runs after, under its 20% target each time; the same prompts gave 0 to 4 noisy decisions of 5 to 7 on the three cases that moved, and the judge rated one unchanged decision both ways, so the runs don't show the prompt did it, and one run on the old prompts can't rule it out. Three cases have guidance: a tenant filter lost on one path with a Look for preference on tenant isolation, a paging bug beside a leftover `console.log` with a Don't flag on debug logging, and a migration with no down section under a `REVIEW.md` that asks for one. In three runs each, every expected mark came back and no other (`guidanceFollowed` 2 of 2, `leftOutRight` 6 of 6, `guidanceWrong` 0 of 5), and the bug beside the left-out `console.log` was found unmarked each time. What a Don't flag preference covers still reached the brief's watch line and its mismatches in three runs of three; a sentence for the intent task is proposed in stage 59's notes and isn't in.

**Marks.** A finding can carry a guidance mark: a ref and an effect, `raised` or `left-out`. The server checks each against the run's guidance: the ref is one the run had, a Look for preference only raises, a Don't flag one only leaves out, and a guideline file does either. A mark on a file left to be read needs a read of it by that pass. A mark that fails is set to none and logged, never retried, and its point stays. `pointsOf` turns a mark into what the page shows, the effect with the preference's text or the file's path, from the guidance on the analysis, so a mark is never read against today's preferences.

**Refs in prose.** The refs number what the prompt gives and name nothing on the page. On a run with guidance each pass's message says a ref goes only in a field that takes one, and that text names a guideline file by its path in the repository and a preference by what it says. Before it, 7 of 12 eval runs with files to read wrote one in the brief, a mismatch or a decision ("the handbook (g3)"). The server takes out what's still written: a file's ref becomes its path, or goes where the path is right before it, and a preference's goes, in every text of an answer the reviewer reads. That's among the call's problems, and never a retry, since nothing is left for the model to fix. A ref-shaped word that isn't the run's stays, and so does one the pull request's title, description or code has as a word, since a geometry change has a `p1` of its own and a point posts as the reviewer's comment.

**Review signals.** A dismissed or raised point is in `point_reviews`, but its text is in the analysis, where Remove AI review takes it away and a new run reuses its ID. So what the reviewer did is recorded in rows of its own, with the text as it was: `dismissed` or `raised` with the point's kind, always a finding since risks and decisions went, title, explanation and file, and `comment` with the body of a line comment the host accepted, in a published review or from Comment now. Deriving them from `point_reviews` and the analyses, as the review activity is derived, was the alternative. A signal is keyed by what made it. For a point that's the analysis and the point, so its latest state stands and reopening it removes the signal. For a review's comment it's the analysis, the review's number and the comment's key, so a retried publish writes each once. Comment now has no number, so its key is the analysis, the lines and the time it was posted. A reply is no signal: it answers someone. A signal that can't be written is logged, and never fails the point's state or the post.

**Proposals.** A suggestion is one request for one repository, with the result as its response: one model call of some seconds. A run with stages and events, as an analysis has, was the alternative for a call with one stage. `POST /api/preferences/suggestions`, with the repository, reads the 200 newest signals on its pull requests, and the reviewer's own comments on the code of its 30 most recently updated pull requests they reviewed, through a port of its own, `ReviewHistory`, apart from `GitHost` for the reason threads have theirs; a host without the port gives the signals alone, and a read that fails fails the request with the host's reason. A comment posted from megareviewer is a signal and on the host too, so `mergeEvidence` sends it once: a comment signal goes when the host has its words on the same pull request, punctuation Bitbucket escapes and spacing aside, and the host's repeats on one pull request go after the first. The same words on two pull requests both stay, since a rule rests on repetition, and a dismissed or raised point is never a repeat. With nothing left to read there's no call and no proposals. Then it makes the call over that, every preference and the rejected proposals, on the chosen model option, or the default as a model run picks it; an option that can't run, or whose provider can't make this call, answers `model-unavailable` with why, before anything is read. A second request for the same repository while one runs joins it, so a double click isn't two model calls. Two requests, one over every repository's signals and one over a repository's host, were the version before, with a count of the signals recorded since the last suggestions, kept in a table of its own, to say when there was something new; a suggestion now reads whenever it's asked, so the table is dropped.

The model's drafts become pending proposals, `learned`, each with at most 5 lines of evidence; `imported`, the source an import gave its proposals, still parses. A blank draft is left out, and so is one that says, whatever its case and spacing, what a preference or a pending or rejected proposal already says: a rejected proposal staying away shouldn't rest on the model's care. A draft is for the repository unless it says everywhere. Finding a draft's repository from the `owner/repo` its evidence names was the version before, when signals came from every repository. Accepting makes a preference of the proposal's source with whatever the reviewer changed. A proposal's text is the model's and can run past a preference's 300 characters; accepting it then needs an edit, where cutting it would change what it says.

**The routes.** `GET /api/preferences` answers the preferences, the pending proposals, and a section per repository: those of the 50 most recently updated analyses, then the others that have a preference. A repository's section is its latest harness, the one put in the store last: each guideline file with its switch and how a review uses it (`use`: in the prompt, on request, or not), and the files it reaches with theirs, each with the file nearest the root that links it, and what the walk left out. A linked file's `use` is with its root on, so a root that's off says what it would bring. The harness's first linking file was the alternative for the grouping, and can be under another root. While a pull request's harness is loading or couldn't be loaded, a note says so, so a list without links isn't read as a repository without any. A repository without a harness has its guideline files alone, at the base commit of its latest analysis, all five paths in one request the first time and from the cache after; one never analyzed, or a read that fails, has no list and the reason instead. `POST /api/preferences`, and `PUT` and `DELETE /api/preferences/:id`, write a preference, `PUT /api/preferences/proposals/:id` accepts or rejects a proposal, and `PUT /api/preferences/guidelines` switches one of the five paths, or any file of the repository's latest harness, and answers the section again: one switch changes how other files are used, by the budget and by what it links, and the page would need the whole harness to work that out. `GET /api/analyses/:id/harness` says where an analysis's harness stands, `loading`, `ready`, `none` or `failed`, with the files a run would put in the prompt and how many more it could read; a route of its own, read live, since a harness isn't part of an analysis. A preference's and a proposal's ID is a hash of what it says and when it was made, as an analysis's is of its key, with a counter when that one's taken, so the server needs no source of randomness.
