# Guardrails

A guardrail is a check that would catch a kind of problem before review, in any code. [DESIGN.md](../../DESIGN.md) says why megareviewer names one, and where.

**The guardrail call** is a model call of a run once its passes have ended, on the run's option, when the run has a finding. It reads the run's findings, those a Don't flag preference left out among them, each with the lines it rests on as its hunk shows them, at most 40 and the rest counted; the intent's mismatches no finding names aren't asked about. It reads too the check configs and build files at the PR's base commit through the file cache, for the languages of the files the points are in. A config's or build file's read that fails, or one over 32 KB, is a warning, and the call goes on without it. It runs on the one-call runner every transport has for the suggestion call (`RunOneCall`), with its own system prompt, schema and data in its one message, at medium effort; on opencode it's an agent of the server's config, `megareviewer-guardrails`, so opencode's prompt version moves with the call's prompt. The passes don't read configs: their system prompt, tasks, shared text and answer format are byte for byte what they were before the guardrail, and Claude Code's and Codex's prompt fingerprints are what they were then. The first version put a `<repository_checks>` block in the passes' shared text and a `guardrail` field in the findings task, and asked again behind a button on a draft; the second grouped the reviewer's comments across pull requests and kept the groups in a table of its own. DESIGN.md says why both went.

**The check configs.** `biome.json` and `biome.jsonc`; `eslint.config.{js,mjs,ts}` and `.eslintrc.{json,js}`; `tsconfig.json`; `ruff.toml`, `.ruff.toml` and a `pyproject.toml` with a `[tool.ruff` table; `.golangci.{yml,yaml}`; `.rubocop.yml`; Checkstyle's `checkstyle.xml` and `config/checkstyle/checkstyle.xml`; PMD's `pmd.xml`, `ruleset.xml` and `config/pmd/ruleset.xml`. The build files, `package.json`, `pom.xml`, `build.gradle` and `build.gradle.kts`, are read for the model only, so it prefers an engine the repository already uses; they never verify anything. A monorepo's nested configs aren't read. The run keeps what it read without the content on its guidance (`guidance.checks`, a build file with no tool), and Remove AI review clears it with the run.

**What the model answers** is a list of marks, loose on purpose, since the server checks everything: each the finding it's on by its ref (`f1`) and a guardrail, a kind of check, an engine, a tool and a rule's name when it's a rule of a configured tool, whether the repository has it on, and one sentence of what it would assert. A point without a mark has none. A tool the schema doesn't know parses as none.

**The server's checks.** A mark naming a point the run doesn't have is dropped, and of two on one point the first stands. `guardrailOf` turns a mark's guardrail into one of two, or none. A rule of a tool whose config the repository has at the base commit, and the PR doesn't change, is read against the config: `rule` when the config doesn't name it, whatever its case (for Ruff, a quoted selector of the rule's own linter that prefixes its code, `"B"` for `B006` and never for `BLE001`, which is another linter's, or `"ALL"`, names it), and the model says it's off; none when the config names it or the model says a preset turns it on, since there's nothing to move to a check. A config the PR changes verifies nothing, so a rule of its tool falls to a suggestion. Anything else with a kind, an engine (`/^[A-Za-z0-9 .+#_-]{1,40}$/`) and a sentence of at most 160 characters is `suggested`, unless the model says the repository already has it, which megareviewer can't check and so doesn't say. A rule's name is a name and nothing else (`/^[A-Za-z0-9@/_.:-]{1,80}$/`). Run details lists every mark left out, and why, as the call's problems. A kept guardrail is set on its finding, beside its guidance mark; `pointsOf` passes it to the point. A guardrail an earlier version stored, without `is` or as `configured`, reads as none, never as an analysis that doesn't parse.

**The landing.** The passes end the run as before: their stages are done, the landing plays, and the review is there to read. When the call will run, the write that ends the last pass sets the analysis's `guardrails` to `running`, which isn't a stage, so the page's `inProgress` doesn't wait for it, and the passes' end is never announced as the run's: the events go on (`following`), that end announced as an update rather than `done`, and the call's end writes the marks and sends `done`, when the page reads the analysis again. Setting it in a write of its own after the passes was the alternative: the page could read the analysis between the two, see nothing running, and stop following before the marks. The marks then go in one render later than the rest (`useMarksHeld`), once the line of code at the top of the window is noted (`holdTopLine`), and that line is put back before the frame is painted, so a line opening on a card above it doesn't move the code being read; the landing doesn't play again, since it plays only on the run's own end. A failed call, an answer outside the schema or one over 30 seconds (`Clock.wait`, so tests control the time) leaves the review as the passes made it, `guardrails` `failed`, and the call's record saying why; with no finding there's no call, and `guardrails` stays null. A stop during the call fails it at the next start, as a stopped pass is. Remove AI review refuses while the call runs, as it does while the passes run. The call's usage and record are the run's, under the name `guardrails`: `ModelUsage.pass` and `ModelCall.pass` are a `ModelCallName`, the passes and the call, and the two passes since removed, so Run details lists it and the usage line counts it, and `ModelPass`, which every transport maps to a pass's prompt, is the passes there are. Through Claude Code on Sonnet 5.5 the call took 1.2 to 3.9 seconds on the eval cases, $0.004 to $0.015 at API prices (`evals/reports/2026-11-22/guardrail-call.md`).

**On the page.** One component says a guardrail in two forms: "A check could catch this: `BLE001` in Ruff, which `ruff.toml` doesn't turn on." with a shield, and "This looks checkable: an architecture rule in ArchUnit. Services never import a controller. Suggested by Claude, not checked." with a shield and a question mark, the family named as the bar names it. It's a line of its own on a finding's card, and a point a preference left out shows it once unfolded. A saved draft a point with a guardrail made, by its Add to review or Edit, shows the line with "Add to comment", which appends "A check could catch this next time: `BLE001` in Ruff." (or the kind, engine and what it would assert) once. The draft is the point's when the point is raised, its card on the draft's part, and the draft on the line raising it put the comment on; a field naming the point on the stored draft was the alternative, a change to the drafts every browser keeps, for what the page can already tell. A draft the reviewer started on a line has none. The line is in the hunk card's slot under a saved draft. No routes are added: the marks are on the analysis.
