# Design

How code review should work now that most code is generated. See [MISSION.md](MISSION.md) for why.

## What review is for

1. **Catch defects:** bugs, security holes, regressions.
2. **Guard the design:** does this change belong here, and is it the right approach?
3. **Spread understanding:** at least one person besides the author knows how the system works now.
4. **Accountability:** a human signs off.

Generated code strains all four. There's far more code, the author often doesn't fully understand it, and the intent lives in a chat transcript nobody sees. Understanding suffers most: if nobody really reads the code, nobody understands the codebase.

## Why the diff view fails

The diff view was designed for a world where code was expensive and every line was written on purpose.

- Files are ordered alphabetically, so the reviewer has to rebuild the story.
- Every line gets equal weight: a lockfile bump looks as important as a removed auth check.
- It shows changed text, not changed behavior, so the reviewer simulates the program in their head.
- The intent is missing: what was asked and which alternatives were rejected.
- Comments attach to lines, but real concerns are about decisions.
- Nitpicks waste attention when code is cheap to regenerate.

## Thesis

> Review should stop being "read every changed line." It should become "understand the change, check what the machine found, and read the code where it matters."

## Principles

1. **Start from intent.** Open with what was asked (ticket, prompt, or agent-session summary) and a plain-language summary of what changed in behavior. The first question is "does this do what we wanted?"
2. **Sort every change by risk.**
   - *Mechanical:* moves, renames, formatting, generated files. Collapsed, with machine proof (e.g. "moved code verified identical").
   - *Logic:* ordinary code changes. Normal read.
   - *Contract:* public API, schema, permissions, dependencies, config, security boundaries. Where human attention goes.
3. **Guided tour.** Start at the entry point and follow the call graph, so the review reads like a story, not a file tree.
4. **Review points, not lines.** Extract what looks wrong, a finding ("retries a charge after it succeeded") or a difference between what was asked and what the code does, as a ranked list on the code it rests on. Each point is raised as a comment or dismissed; saying nothing means it's fine.
5. **Evidence over code.** Show tests run and their coverage, before/after outputs, sample requests and responses, and UI screenshots.
6. **Machines go first.** AI and static tools look for bugs first. Humans see only the findings machines are confident about, as points on the code; nits are fixed automatically, never discussed.
7. **Ask the code.** The reviewer can ask questions ("what if `user` is null here?") and get answers grounded in the code, without checking out the branch.
8. **Close the loop with the agent.** A reviewer comment becomes an instruction to the agent; the reviewer re-reviews only the resulting delta against the point they flagged.
9. **Depth matches risk.** Low-risk changes get auto-approved or a quick look; contract changes get a deep review. The tool picks the depth and says why.
10. **Review the plan before the code.** Approving an agent's plan is the cheapest review. Code review then becomes a conformance check against the approved plan.

## Decisions

- **Product form:** standalone web UI, served locally by a CLI, with no server of ours. See [ARCHITECTURE.md](ARCHITECTURE.md).
- **First slice:** take a GitHub or Bitbucket Cloud PR and produce a guided review: an intent summary, hunks sorted by risk with mechanical ones collapsed, and the points worth the reviewer's attention on the code. This covers principles 1–4, which the rest build on.
- **Files, read whole, in path order.** The page shows each changed file once, all its changes on one card, in path order as a directory tree lists them. The call graph's story is in the overview's diagram. The guided tour by steps was the first version: a file several flows run was cut into a piece per step, five pieces of hosts.py on delphi-code #2, and the reviewer had to put it back together. Call order came next and left the page with the elements built around it, when the page was cut back to its primitives.
- **Shared code is read once.** When several of the code's flows run the same changed code, it's read in a section of its own before them, and each flow points back to it instead of the first flow reading it all. Tests go with the code they exercise, and every changed part is still in the flows exactly once. Reading it in the first flow was the first version: on delphi-code #2 the first route's flow held half the PR, because the other two routes run the same connection and keychain code.
- **A call shows the code it runs, where it is.** Resting the pointer on a call into code the PR changes opens that code in a card under it, which stays while the pointer is on it. Files are in path order, so the code a call runs is usually elsewhere on the page, and following a call is how a reader checks what it does. Going to the code lost the reader's place, and chips under every call were noise.
- **Code outside the PR is always at hand.** Who else calls what a PR changes is where a regression shows, and showing it needs the repository. A clone on the reviewer's machine is read when it has the PR's head commit; otherwise megareviewer downloads that one commit into a copy of its own, without being asked. The review opens right away, and the callers come to it seconds later, without moving the code being read. Asking first was the alternative: a question before a review for something that reads what the reviewer can already see on the host, and whose answer is nearly always yes; a button would leave the callers off every review whose reviewer doesn't know it's there. What it costs is said where it can be read: the startup summary names the folder and `--no-download`, which turns it off, `doctor` lists the copies with their size, and a copy nothing read for 30 days is removed. megareviewer never fetches into the reviewer's own clone, even one that only lacks the commit: it's theirs.
- **The review says how much it read.** A PR that nothing outside calls and a PR whose repository megareviewer never saw looked the same: no callers on the code, and the reason at the bottom of the Details dialog, which a reviewer who doesn't know to look never opens. So the header's byline says it after the repository's name, always, in words with an icon: Whole repository, Downloading repository…, or PR only. It opens where the repository was read from, the reviewer's clone or megareviewer's own copy, at which commit, and how many uses outside the PR were found, none among them; or why it wasn't read and what would fix it. The first two are muted like the line they're in, and PR only is in the text's color, since that's when the reviewer has less than they'd think. Showing it only when the repository wasn't read was the alternative, as the review status shows only when it says something; but then Whole repository is said by nothing, and nothing is what a reviewer sees when megareviewer hasn't looked. The bar was the other place: it stays in view, but it's one row for what the reviewer acts on while reading, and this doesn't change while they read.
- **The model is optional.** Without it, the review is built by deterministic code: risk from rules that can only mark a change *contract*, flows that follow the call graph with tests next to their code, and mechanical proofs as before. Request AI review, a button on the review, adds intent and its points to the analysis in front of the reviewer. The page has to be good enough to review with before any model call, because each reviewer pays for their own, and a review that's useless without the model is one nobody runs until they've set up credentials. The model always on was the first version; with it, the page without credentials was an error. A flag at startup, `--ai`, was the version before the button: the reviewer had to know it and restart to get the model, for every PR or none. The model is the reviewer's choice, on the button: its menu lists every model megareviewer knows on every provider, the ones the machine can't run disabled with why and the fix, so a reviewer learns what signing in to another provider would add. Hiding them was the alternative. The last model used is remembered across restarts, so a reviewer who prefers another one picks it once. Sonnet 5.5 is the default, because on the evals it says far less that's wrong than Haiku for cents more a PR.
- **A tour of the PR, to understand it before reading it.** Between the brief's three lines and the files, nothing said what happens and in which order, so understanding a PR meant reading it. The tour is a few steps in call order, from where the change is reached to what it ends in, each one sentence of what happens there and the few lines that decide it, real diff lines the reviewer comments on as in the map. In about two minutes the reviewer knows what the PR does and how, and whether anything is fundamentally wrong, then approves from the bar or goes to the code. It's a layout of its own, Tour, the third in the bar's switch beside Code and Overview, there once a run has written a tour: a strip of the directories the tour's path runs through, the steps, then what the tour didn't show, every changed line no step shows, counted from the diff by file, so the steps' lines and the ledger's add up to the PR's; Claude's findings outside the steps; and which steps to read in the code, by a rule: those with an open finding. The model writes only the steps, in a pass of its own; the boxes are the overview's directories, the chips on a step are the analysis's points on its lines, and the depth is the rule, so nothing in the tour is a second wording of what the page already says. The tour is on unless the reviewer turns off the Display menu's Tour (preview) switch, and the page still opens on the code. Off, the page and every request are what they were before the tour. Off by default was the version before: a reviewer who hadn't found the switch never saw a tour, and one who had turned it on every time megareviewer started, since the choice is kept in the browser's storage and without a fixed `--port` every start is a new origin. Now it's turning it off that has to be repeated, which costs the reviewer who does one more pass that reads the PR from the cache: on delphi-code #2 $0.05 of a run's $0.74, done before the findings were. Without a tour there's no Tour in the switch, and the Overview is its diagram with a tour or without. The Overview showing the tour in place of its diagram was the version before, with a line saying why when there was none: a reviewer who wanted the directories after an AI review had lost them to the tour, and the switch's second button meant two things. Open in code shows the map on a step's lines, marked on their numbers in the primary color under a label naming the step, and the bar's switch, Esc, `v` and the browser's Back come back to it; `v` and the bar's switch go between the step last current and its lines. A second row under the bar, Back to tour, was the version before: the switch beside it already went back, so it said the same thing twice in a row of its own, and Understand was the layout's name while it showed the tour, so the switch's second button changed its name with a switch in the Display menu. A spotlight over the map, dimming the code a step doesn't show, would have kept the file order the tour exists to get past; the tour as the first screen would have put a model's reading in front of every review, the intro panel reviewers skipped. The designer's version differed where the product does: its ledger listed files without a step, so a step showing 8 of a file's 164 changed lines left 156 in no list; without the model it drew a flat row of boxes, worse than the overview; while the passes ran it counted directories read, which nothing knows, since the passes read the whole PR at once; it added a row under the bar with a second Display menu, a line of code on every screen; and its Esc left the tour for the code while the map's Esc came back, so the two bounced. A step's chips open the point's card in the map rather than dismissing or raising it in place, and steps have no keys of their own.
- **The overview as flow paths, in three forms to compare.** The overview draws the changed directories and the calls between them, and on a typical service that's controllers, services and repositories: the architecture, the same on every PR, so it says nothing about this one. It also made a box of every test directory whose tests it couldn't link to code, which in Java is most of them, since a test is in its class's package and another source root: on graal #15134 four of the strip's seven boxes were test directories. Boxes by module and layer were the first answer and were rejected for the first reason: a better drawing of what the reviewer already knows. What a PR has of its own is how it's reached and what runs from there, so the previews draw flow paths: each way the change is reached, a route, a page, a command, or the definitions nothing in the PR calls, with the changed files it runs in call order, new ones told from changed ones, and the requests it sends to the PR's own routes. Tests aren't on a path at all, nor docs, generated or mechanical files: they're listed under it by kind, every one a link to its code, so no changed file is missing from the page. Nobody knows yet which drawing reads best, so there are three behind a choice in the Display menu, Overview (preview), kept per browser, with Directories, today's overview, the default. **Lanes**: a column per directory, callers first, and a row per path with no lines between its marks, so the architecture is the table's headings, read once, and a mark is only where this PR changes something. **Bow tie**: where the change is reached on the left, the directories it runs through in the middle, what it ends in on the right. **Flow rows**: no diagram, a small tree of chips per path, each file after or under one that calls it. A path runs definitions, not files: a call into one method of an added class reaches that method and what it calls. By file was the first version, and on graal #15134 a one-line call was a path of 17 files, 15 of which it doesn't run. A link between two files is a call the path makes, in every form: the first version drew each path as a chain of its files, and a third of graal's arrows joined two files with no call between them. On delphi-code #2 that's four paths, the page's ending in its three requests to the routes; on graal #15134 ten, over eleven directories, which lanes scroll sideways for. They're as good as the entries that are recognized: megareviewer #3 has five paths from the components of three files, and the rest start at definitions nothing in the PR calls, an override or a callback a framework reaches. Code outside the PR that uses what it changes is a count on the changed file or directory, “used in 4 places outside the PR”, and starts no path and has no box in the overview's directories. A row or a faded box for each such file was the version before: a regression would show there, but on graal #15134 they were 13 of 19 rows, 11 of 20 boxes and 17 of 31 edges, and the reviewer reading what the PR does was looking at files it doesn't touch. Where the code is used is read where it is, on its card in the map. What a path ends in beyond a request, a table written or a service called, isn't known without the model, and an unchanged route that reaches changed code through several calls needs callers of callers from the checkout. One form, picked by us, was the alternative; three cost little while they share one model, and two of them go once reviewers have used them.
- **Primary users:** both. A solo dev reviewing their own agent's output needs to *understand* it; a teammate reviewing someone else's PR needs to *trust* it. The same review has to serve both.
- **Intent sources:** intent is extracted, not entered by hand, from:
  - the PR description;
  - Jira tickets mentioned in the description, commits or branch name;
  - the code itself, inferred from what the change actually does.

  Stated intent (description, tickets) and intent inferred from the code are compared. A mismatch between them is a finding in itself: the change does something nobody asked for, or misses something that was asked. So the two are shown side by side only when they disagree. When they agree, one line says the change does what was asked, and the full list of behavior changes sits behind a toggle. Always showing both was the first version. It said the same intent twice and made the intent panel the biggest thing on the page.
- **Intent is one line.** Before the code the reviewer reads what the change does, as behavior a user or caller notices, in at most 20 words: Claude's once it has run, and the description's first sentence before. A brief of three lines was the version before: what the change does; how it runs through the system, from where it's reached to what it ends in, by the names of its page, routes and modules; and what to watch, at most two things the first line leaves out, something nobody asked for first, then what changes for code, users or data that already exist. Before a run the code wrote the other two lines itself, the overview's directories in call order with their entry points and the changed definitions code outside the PR uses, with how many uses. On graal #15134 the three lines wrapped between the title and the code, and the reviewer had come for the code: the directories are the architecture, the same on every PR and already the overview's, the uses are on the code, under each part's “Used unchanged in”, and what nobody asked for is a mismatch, marked on the code it rests on. The intent pass writes only the summary now, so a run pays for nothing the page doesn't show. One sentence was the version before the brief, and said the title again in more words, which the task still forbids. A watch line that could name what looks wrong was tried on the evals and dropped: it said a finding before its card did, a second time.

- **A point is a finding.** What the model asks the reviewer to look at is what looks wrong: a finding, or an intent mismatch no finding names, in one ranked list. A finding is a draft comment under the line it rests on, with its type, Claude's severity and a suggested change when the fix is a few lines; the type and the severity are Claude's and stay on its card, so the comment the reviewer adds, and every comment on the PR, carries neither. Add to review saves it as the reviewer's draft, Edit opens it in the comment box first, and it posts with the review under their name; Dismiss folds it. Its lines are marked on their numbers, in its severity's color. Silence means fine. Nothing else is a point, and nothing else becomes one: a finding says something looks wrong and asks for a change, and a choice that's intended but has a consequence isn't that. What nobody asked for is an intent mismatch, and so is what changes for existing code, users or data without being asked.

  Two other kinds were the version before, and neither earned its place. A **risk** was a hunk the model marked contract, with its reason, as a note under its lines: code worth reading closely, with nothing wrong. It was a classifier's output shown as a point, and a classifier can't triage: every hunk it marked was a card that asked the reviewer to stop, 25 of them on delphi-code #2 and still 8 after the prompt kept only where a mistake would break something outside the PR, and reviewers read them as noise. A **decision** was why the code makes a choice, a chip at the end of its line that opened a footnote. It was off until a switch in the Display menu turned it on, because with it on a PR whose description explains its choices read them twice, six of eight times on delphi-code #2, so nobody opened it. Before that the two were cards of a finding's shape, a band over the code, a margin bar, and approve and reject on each decision, seven clicks to say "fine". A risk also named the test that checked it, when one did: "Checked by `answers 404 for another user's order`". It answered "should I stop here?", and there's no risk left to ask it of. A preference such as "any change to billing" used to make a hunk a risk, and then the brief's Watch line said first that the change touches it; now a finding carries its mark when something there looks wrong, and nothing is said when nothing does.
- **A finding is about logic, a contract or the architecture.** The findings pass looked for bugs only, and two things a reviewer is there for went unlooked for: what the change breaks outside the PR, and whether it's built in the right place. It now looks for three types and says which each finding is. **Logic:** the code does the wrong thing. **Contract:** the change breaks or exposes something outside the PR, a caller, stored data, a security boundary, a user or another service, a dependency or configuration. **Architecture:** it's built in the wrong place or the wrong way for the code the PR shows. A finding that's both is contract, since outside the PR wins. Contract is the name a hunk's risk class has too, on purpose: both mean the boundary between the PR and what's outside it.

  The bar is the one a logic finding always had, what's wrong, shown by code the model read, and a change to ask for; without it the risks would be back as minor contract findings. So a contract finding names who breaks and shows it: "`chargeOrder` in billing/charge.ts still multiplies by 100", not "this changes the response shape". A change that only could break something is no finding. For that the model reads the unchanged callers, which is where a contract break shows and which only the page showed until then; a run started before they arrive reads the PR without them. An architecture finding rests on what the PR and its callers show, since the model doesn't read the codebase, and "this belongs elsewhere" is a guess unless the elsewhere is in the data. It's one of three things: a dependency that points the wrong way between files in the data, a layer the other code goes through and this code skips, and logic written again that code in the data already has. Naming, style and "consider" stay out for every type. Architecture was to be dropped if it brought wrong findings; on the evals it brought none, in two cases made for it, so it stays with that said.

  A type is a label and a filter: a word on the card, and a chip per type on the bar that narrows the stepper to it. Sections by type were the alternative; a run has at most 10 findings and usually a few, so a heading would often sit over one. **Severity ranks.** The stepper and its list go blocking first, then major, then minor, in the model's order within each; the model's order alone was the version before. **Severity takes the colors:** a finding's marks, its bar and its glyph are blocking red, major orange or minor amber, each with its word on the card. A color by kind, a finding red, a risk amber and a decision grey, was the version before, and a color per type was rejected: three more hues that mean nothing until learned, on a page where red, orange and amber already read as levels. A mismatch no finding names has no type and no severity, comes after the findings, under no type's chip, and is grey.

- **Contract is the rules' alone.** A hunk's risk class, *mechanical*, *logic* or *contract*, comes from a mechanical proof or a rule on its file's path, and is internal: it orders the flows and is never shown, since a rule reads the path, not the code. The model no longer classifies hunks, so a run changes no hunk's class. A count of contract parts in each file's header, the tree and the overview was one version before, with the rule's reason ("auth or security path"): it said where to look without saying why.

- **An AI review follows what the reviewer values.** Request AI review said the same things to every reviewer: one who never wants a comment about naming got one on every PR, and one who cares most about tenant isolation had to hope Claude thought of it. megareviewer now keeps the reviewer's preferences, on their machine, and gives them to the passes. A preference is a rule, one short sentence, with a kind, **Look for** or **Don't flag**, a scope, everywhere or one repository, and a switch; a run reads the enabled ones for everywhere, then the PR's repository's. Free-text notes per scope, like a CLAUDE.md, were the alternative: a point couldn't then say which preference shaped it, and a learned proposal would be a line appended to prose. Global only leaks one codebase's rule into another; per repository only makes the reviewer write "no naming nits" in each. Preferences change what's flagged, and not the wording of comments: a comment posts under the reviewer's name, and they edit it before it does. They can't touch the safety rules: text in a PR aimed at an automated reviewer is still a finding, a mechanical proof is still the code's, and a path rule's contract still orders the flows.

  They come from three places. The reviewer writes them. A repository's guideline files, `REVIEW.md`, `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md` and `.github/copilot-instructions.md` at its root, are detected, and the reviewer switches them on: `REVIEW.md` is on unless switched off, the others off unless switched on, since they're about writing code and can be long. And megareviewer proposes rules from the reviewer's reviews, in two ways: at the point, where Dismiss has "Don't flag things like this", which opens a rule drafted from that point for the reviewer to word and save, with no model call; and on request, "Suggest from my reviews" on a repository, one model call over what megareviewer recorded the reviewer doing on its pull requests, the points they dismissed and raised and the comments they posted, and the reviewer's own comments on its host, each comment once. Two buttons were the version before, "Suggest from my reviews" over what was recorded in every repository and "Import from my past reviews" over one repository's host: they ended in the same proposals, and the first was disabled until megareviewer had recorded enough, which on a new install is every repository. Learned means proposed: megareviewer never turns what the reviewer did into a rule by itself. A proposal says what it would add and what it's based on, and the reviewer accepts it with Add, to edit it as any preference after, or rejects it with Dismiss; a rejected one isn't proposed again. Applying learned rules at once, with a page to remove them, was the alternative: a review that changed and didn't say why. Sending the model the last dismissed and raised points as examples was the other: nothing the reviewer can read or correct. A model call after every publish, and reading the host's history at the first review of a repository, were both rejected as requests and a model call nobody asked for, on the reviewer's plan. Everyone's comments on the host were the alternative to the reviewer's own: the team's habits, which aren't this reviewer's preferences. A proposal's words come from a model reading point titles, which come from PR text, so a PR could try to plant a rule; a proposal is only ever text the reviewer reads and accepts.

  A point says which preference shaped it, "From your preference: check tenant isolation" or "From REVIEW.md", and the mark stays right after the preference is edited or deleted, because the run keeps the guidance it was given. "Don't flag" folds, it doesn't hide: Claude still reports a finding such a preference matches, marked as left out, and the page shows it folded to one line with the preference and Show. Not reporting it was the alternative: cheaper, and the reviewer never learns what a rule removed, or that it's too wide. Keeping only the major and blocking ones was the other. A mark that doesn't check out, one naming a preference the run didn't have or "left out" by a Look for preference, is dropped, never the point: unsure, the page shows more. At most 50 preferences can be enabled per scope, and the 51st is refused with a message, since sending the first 50 of more would drop the rest silently; for the same reason a guideline file that doesn't fit the prompt isn't cut but left to be read, or left out where nothing reads it, and the page says so.

- **A repository's rules are its guideline files and the files they link.** A root `CLAUDE.md` or `AGENTS.md` is often an index: megareviewer's own is 310 bytes and names the documents with the rules in them. So megareviewer finds a repository's **harness**: the five guideline files and, from each, what it imports (`@docs/rules.md`), links in Markdown or names in prose, a `.md`, `.mdc`, `.markdown` or `.txt` file of the repository's. A path in a code span or a fence is an example, not a link. Every Markdown file in the repository was the alternative: of megareviewer's 104 that adds the eval cases' fixture files and each adapter's `PROVENANCE.md`, which are nobody's rules. Links alone already reach 81 files and 1 MB there, since `CLAUDE.md` names the plan README, which links every stage doc, so being reached isn't being read: an import is the author saying "always load this", and is in every review while it fits; the rest, and what doesn't fit, a pass opens for itself when the change calls for it, with a reader of those files and nothing else. Never a tool was the rule before, and is still the rule for everything a PR could aim at. Whether reading makes a review better isn't known until the evals say; until then a reviewer meets it only by switching on a root file that links others. Every read is in Run details, and a point is marked with a file only when its pass was given it or read it.

  Each file has a switch of its own and is on unless switched off, but only through a root that's on: a root's switch is the reviewer's say on everything it brings, the roots it imports among them, straight or through the files it imports, so a `CLAUDE.md` that is only `@AGENTS.md` brings `AGENTS.md` when it's on, unless `AGENTS.md` itself is switched off. A root another one only links or mentions keeps its own switch and default. Every root by its own switch alone was the first version, and such a `CLAUDE.md` brought nothing. Loading starts when a PR is opened, so it's there when the reviewer asks for an AI review, and nothing waits for it or fails with it. Loading on Request AI review was the first version: the run then starts with requests to the host. The preferences page shows what a root brings before it's switched on, and Request AI review's tooltip what a run would read, since a reviewer who pays for every token shouldn't learn from the bill what `CLAUDE.md` links.

- **A check instead of a fix.** A finding says what's wrong with this code, and the author fixes it there; when a check could catch that kind of problem in any code, a lint rule, a compiler option or an architecture rule, the better answer is the check, which ends the problem for the whole team before review, as the sixth principle asks. So after an AI review's passes, one model call, the guardrail call, reads the run's findings with their code and marks each one a check could catch, with the check. Who found it doesn't matter, Claude or the reviewer: the goal is the check. It needs no history, so it works on the first review of a repository, and nothing is kept between pull requests: the mark is on the point, in the analysis, and goes with Remove AI review.

  The line is on the finding's card, and on a saved draft its Add to review or Edit made, with "Add to comment", which appends one sentence naming the check; a draft knows its point, so no words are compared. megareviewer writes nothing in a comment without a click. Two versions came before. The first asked on a draft, behind "Could a check catch it?", one call on the click, and nobody clicked; it also put the repository's configs in the text every pass shares and a `guardrail` field in the findings task, which every change to the passes then has to be measured again for. The second asked inside Request AI review what the reviewer keeps saying: it grouped their comments and raised points in a repository by meaning, kept the groups, and showed them on a chip in the bar, on a finding and on a draft matched by words. It needed comments on three pull requests before it said anything, it read only what the reviewer said, and a draft's words missed: "swallowing" isn't "swallow". Counting, per repository, how many pull requests each check would have caught something on is the alternative kept for later: it would rank the checks by the check's own name, which is exact.

  A guardrail catches a kind of problem, not this one: a lint rule, a compiler or type-checker option, a formatter, a pattern rule somebody would write, an architecture rule, or a check in CI such as an API-compatibility check or a scanner. A test of this one behavior isn't one, since "a test could catch this" is true of every bug, and a matter of judgment gets none. Marks are rare, and that's accepted: the findings pass leaves out style, naming and missing tests, most of what a linter catches, and most of what it finds is a logic bug no check decides. When risks were points they were asked about too.

  A guardrail says how sure megareviewer is. A rule it verified is a named rule of a tool whose config it read at the repository's root at the PR's base commit, Biome, ESLint, TypeScript, Ruff, golangci-lint, RuboCop, Checkstyle or PMD, which the config doesn't name: "A check could catch this: `BLE001` in Ruff, which `ruff.toml` doesn't turn on." Verified means the config, not the rule: that the rule exists and would report this is the model's word, and the evals count a rule no label lists with a target of none; a list of every tool's rules in megareviewer was the alternative, thousands of names that go stale with each release. A rule the repository already has isn't said, since there's nothing to move to a check, and megareviewer can't tell a wrong rule from a file that isn't linted; saying "this repository already has a rule for this" was the second version's. A config the pull request itself changes verifies nothing, since the base commit's file no longer says what the repository will have, and a nested config isn't read, so the line names the file it read. Anything else is the model's suggestion, a kind of check, an engine and what it would assert, shown as that: "This looks checkable: an architecture rule in ArchUnit. Services never import a controller. Suggested by Claude, not checked."

  The call starts when the passes have ended, and the review lands without it; its marks come after, without the landing playing again and without moving the code being read. Waiting for it was the alternative: seconds added to every run for a mark most points never carry. The four passes are what they were before the guardrail: the call can only add a mark to a point, never change, add or remove one, and its failure is a line in Run details. megareviewer only names a check: it never changes the repository, and nothing is applied for the reviewer.

- **The main page starts a review within seconds.** A field for a link, then the PRs waiting for the reviewer and their own, then a calendar of the reviews and comments they posted, so they see what they've done and come back to do more. What's connected is a button in the header, said in full only when something's wrong; a setup strip on every visit was the version before. The calendar counts what the reviewer did and never scores it: a streak or a rank would reward approving fast, which is the opposite of what review is for.
- **The reviewer picks the verdict when publishing:** comment (the default), approve or request changes. It no longer follows from counts of clicks, so Publish is offered on any complete analysis: an approval with nothing to say is a review in itself. Choosing was removed from the dialog once, when there was nothing to base it on without decisions; a raised finding is that base now. With silence meaning fine, the published review is the whole record of what the reviewer thought (see the fourth goal above). Publishing again is another review, as on the host: a reviewer who commented can come back and approve once the author has answered. One review per analysis was the first version; after it the bar said only Published, and the way to approve was the host's own page, or a new push and a new analysis. On their own PR the verdict stays in the dialog, approve and request changes disabled, with a line saying the author can't use them; it was hidden there first, and a reviewer looking for Approve found nothing that said why. A comment with nothing in it isn't a review, so Publish waits for a summary, a line comment or a verdict, and says so. Approve is also a button of its own beside Publish, which approves at once with nothing else: an approval is the review a reviewer with nothing to say sends most, and the dialog made it three clicks. It's filled once Claude's run is done and nothing is pending, and an open finding doesn't block it, since saying nothing about a point means it's fine. Nor do new commits since the analysis: whether they need another look is the reviewer's call, so Approve only stays in outline while Re-analyze stands beside it. It was disabled until a new analysis before, which held up an approval over a push the reviewer didn't need megareviewer for. Beside the buttons the bar says the reviewer's own verdict on the host, Approved, Changes requested or Commented, however it was given, and nothing before there's one; "Published", which it said before, only said a review was sent, and an approval from the host's own page went unseen. Once the reviewer has approved, the bar is "Approved" and Revoke approval alone, until a comment waits and Publish comes back beside it: an approval is the whole review until there's more to say. Revoke takes it back at once, so an approval that a later push or a second look no longer earns isn't left for the host's page to undo. It's in outline, never filled, and works on an analysis the PR has moved past and on a merged or closed PR, since taking an approval back needs no fresh look at the code. After changes requested, Approve stays in outline: overturning the reviewer's own block shouldn't be the loudest thing on the row.
